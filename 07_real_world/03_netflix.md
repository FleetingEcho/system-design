# Netflix 架构演进

> 来源：Netflix Tech Blog、AWS re:Invent 演讲、NSDI/SOSP 论文。
> Netflix 是云原生、混沌工程、微服务三个概念的**发明者和最佳实践来源**。

---

## 系统规模（2023 年）

```
订阅用户：2.38 亿
同时流媒体并发：约 1 亿
日视频播放量：数亿次
峰值带宽：互联网总带宽的 15%（北美）
内容库：1.7 万部电影 + 剧集，每部多种分辨率/语言/字幕
CDN 节点（Open Connect）：1 万个+，遍布 1000+ 城市
```

---

## 核心挑战

```
1. 超大文件分发：一部 4K 电影约 15GB，数亿用户同时观看
2. 全球低延迟：世界各地用户启动视频 < 2 秒
3. 自适应码率：网络波动时不卡顿，自动降清晰度
4. 高可用：付费用户体验，不能宕机（SLA 99.99%+）
5. 个性化推荐：2 亿用户，每人看到不同的首页内容
```

## 演进阶段

### 阶段一：数据中心单体（2007-2008）

```
上线初期：传统数据中心，物理服务器，Oracle 数据库
2008 年灾难：数据库硬件故障 → 服务中断 3 天
             用户无法收到 DVD（当时还是 DVD 邮寄业务）

决定：必须迁移到云，消除单点故障
→ 历时 7 年（2008-2016），完整迁移到 AWS
```

### 阶段二：迁移 AWS + 微服务（2008-2015）

**为什么选 AWS**

```
不自建数据中心的原因：
  - Netflix 是内容公司，不想做基础设施
  - AWS 弹性扩缩容（Super Bowl 前一天扩容，第二天缩回来）
  - 多地域容灾（AWS Multi-AZ / Multi-Region）
  - 按用量付费（视频是有季节性的）
```

**微服务拆分**

```
从单体逐步拆出：
  用户服务、账单服务、推荐服务、搜索服务、
  视频目录服务、流媒体服务、设备服务...

峰值微服务数：700+ 个微服务
挑战：服务间调用链极长 → 熔断器变得不可或缺

Hystrix（2012 年开源）：Netflix 发明的熔断器库
  - 每个服务调用都有超时和熔断
  - 故障隔离：A 服务挂了不能拖垮 B 服务
  - 现已退休，被 Resilience4j 接替
```

### 阶段三：Open Connect CDN（2012-至今）

**为什么自建 CDN**

```
2012 年前：用第三方 CDN（Akamai、Limelight）
问题：
  视频流量极大，第三方 CDN 成本极高
  无法控制缓存策略和缓存命中率
  部分 ISP 的网络到第三方 CDN 带宽有限，体验差

解决：自建 Open Connect CDN
  与全球 1000+ ISP 合作，在 ISP 机房内部署专用服务器（OCA, Open Connect Appliance）
  ISP 免费提供机房空间和电力（换取流量不出其网络，省钱）
  Netflix 提供专用硬件（大容量 HDD + 快速 SSD 缓存）
```

**缓存策略：预推送（Proactive Push）**

```
普通 CDN：用户请求时回源取内容（被动缓存）
Netflix：提前把热门内容推送到各 OCA 节点（主动预推送）

推送时机：每天凌晨低峰期
          根据地区流行趋势预测，把"今天会火"的内容推到各地 OCA
          
命中率：95%+（绝大多数请求不需要回源）
效果：全球用户启动视频延迟 < 2 秒（本地 OCA 就有内容）
```

**视频分片与分级**

```
一部电影不作为整体存储，而是：
  1. 切片：每个 .ts 分片约 4 秒
  2. 多码率转码：
       4K HDR（25 Mbps）
       1080p（8 Mbps）
       720p（4 Mbps）
       480p（1.5 Mbps）
       240p（0.5 Mbps）
  3. 多语言音轨、多语言字幕
  
  一部电影在 Netflix 存储系统里约有 1200 个不同版本文件

HLS/DASH 自适应码率：
  播放器每 2-4 秒检测下载速度
  网速好 → 请求更高码率的分片
  网速差 → 降低码率，不卡顿
  分片独立下载，切换码率不需要重新开始
```

### 阶段四：混沌工程（2010-至今）

**Chaos Monkey（混沌猴子）**

```
背景：迁到 AWS 后，Netflix 意识到"任何组件随时可能挂"
      与其等它真的挂，不如主动搞破坏，逼团队把系统设计成能扛故障

做法：Chaos Monkey 随机关掉生产环境的服务实例
      如果系统崩溃 → 说明设计有问题，赶紧修
      如果系统正常 → 证明容错设计有效

演进：Simian Army
  Chaos Gorilla：关掉整个 AZ
  Chaos Kong：关掉整个 Region
  Latency Monkey：模拟网络延迟
  Doctor Monkey：检测不健康实例并下线

结果：Netflix 在 2011 年 AWS us-east-1 大规模故障时，
      是少数几个没有完全宕机的大型服务之一
```

## 推荐系统架构

```
Netflix 主页 80% 的播放来自推荐（不是搜索）

特征（Feature）：
  用户特征：观看历史、评分、暂停/回放行为、观看时长
  内容特征：类型、演员、导演、时长、语言
  上下文：时间（周末vs工作日）、设备（手机vs电视）、时区

算法（多层）：
  离线：矩阵分解（Collaborative Filtering）+ 神经网络
        每天批量训练，生成用户的基础推荐向量
  实时：结合最近行为微调（今天刚看完犯罪片，现在多推犯罪片）
  
  A/B 测试：所有算法变更都做 A/B 测试，对照指标是"播放分钟数"

存储：
  特征向量存 Cassandra（高写入、可扩展）
  实时特征存 Redis（低延迟读取）
  批量训练数据存 S3 + Spark 处理
```

## 最终架构全景

```
[用户设备]
    ↓ 首页加载
[API Gateway（Zuul）]
    ↓
[推荐服务] → Redis（实时特征）+ Cassandra（历史数据）
    ↓
[视频目录服务] → 返回内容元数据
    |
    ↓ 播放请求
[Steering Service] ← 决定从哪个 OCA 节点取视频
    |                 考虑：用户位置、OCA 负载、内容是否在该 OCA
    ↓
[Open Connect OCA] ← 本地 CDN 节点，95% 命中率
    |
    ↓（5% cache miss）
[S3 + 源站] ← 原始视频文件

[监控层]
  EVCache（Netflix 自研的分布式 Memcached）← 会话缓存
  Atlas（指标收集）
  Zipkin（分布式追踪）
  Turbine（Hystrix 熔断状态聚合）
```

## 关键设计决策总结

| 问题 | Netflix 的解决方案 | 为什么 |
|------|-------------------|--------|
| 视频分发延迟 | 自建 Open Connect CDN + 预推送 | 第三方 CDN 成本高、命中率低 |
| 网络抖动卡顿 | HLS/DASH 自适应码率（4 秒分片）| 分片独立，可动态切换码率 |
| 服务级联故障 | Hystrix 熔断器 | 700+ 微服务，一个挂了不能拖垮全部 |
| 容错设计验证 | 混沌工程（主动制造故障）| 真故障比演练更能暴露问题 |
| 推荐效果 | 多层算法 + 全量 A/B 测试 | 80% 播放量来自推荐，直接影响付费留存 |

## 面试可借鉴的点

1. **视频分片 + HLS/DASH**——回答"YouTube/Netflix 如何播放视频"的标准答案
2. **预推送 CDN**——和普通 Pull CDN 的区别，适合内容可预测的场景
3. **混沌工程思想**——面试中提到会非常加分（"我们会主动测试故障"）
4. **多码率存储**——一个视频文件不够，要存 N 个版本
