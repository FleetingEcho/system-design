# WhatsApp 架构

> 来源：Facebook Engineering Blog、High Scalability 分析、OSDI 论文。
> WhatsApp 是**极致工程效率**的典范：2014 年被 Facebook 收购时，55 名工程师支撑 4.5 亿用户。

---

## 系统规模（2023 年）

```
月活用户（MAU）：20 亿
日活用户（DAU）：10 亿+
日消息量：1000 亿条
日语音通话分钟数：数十亿分钟
日活跃群组：数亿个
```

---

## 核心设计原则（不同于其他 IM）

```
WhatsApp 的几个非常规选择：

1. 消息不在服务器持久存储
   → 消息投递成功后从服务器删除
   → 服务器只是中继，不是存储
   → 极大降低存储成本
   → 代价：换设备后历史消息无法恢复（除非手动备份）

2. 端到端加密（E2EE）
   → 服务器看不到消息内容
   → 即使服务器被攻破，消息内容是密文

3. 极简功能（早期原则）
   → 专注做好消息投递，不做推荐、不做广告
   → 工程团队极小但效率极高
```

## 技术栈选择：Erlang

**为什么 WhatsApp 用 Erlang**

```
Erlang：1987 年 Ericsson 为电话交换机开发的语言
  - Actor 模型：每个连接是一个轻量级进程（不是 OS 线程）
  - 可以同时运行数百万个 Erlang 进程（每个只占约 300 字节内存）
  - 内置容错（"let it crash" 哲学）：进程挂了 supervisor 自动重启
  - 热代码升级：不停机更新代码
  - 天然适合高并发长连接场景

单台服务器能支撑多少连接？
  早期目标：单台服务器 100 万并发连接（C10M 问题）
  WhatsApp 实测：单台服务器达到 200 万并发连接
  
  对比：
    Java/Tomcat 的线程模型：每连接 1 个线程 × 1MB 栈 = 100 万连接需要 1TB 内存
    Erlang 进程：每进程约 300 字节 = 100 万连接只需 300MB
```

## 消息投递流程

### 发送消息

```
用户 A 给用户 B 发消息：

[A 的手机]
  1. 生成消息（包含本地消息 ID）
  2. 用 B 的公钥加密（E2EE）
  3. 通过长连接（XMPP over TLS）发送到服务器
  
[WhatsApp 服务器]
  4. 验证 A 的身份
  5. 查找 B 的在线状态和连接的服务器
  6. 把加密消息转发给 B 所在的服务器
  7. 如果 B 在线：立即推送，等待 B 的 ACK
     如果 B 离线：消息暂存到离线存储（等 B 上线）
  8. 向 A 返回服务器回执（消息到达服务器，√）

[B 的手机]
  9. 收到消息，用自己的私钥解密
  10. 向服务器发 ACK
  11. 服务器通知 A（消息已送达 B，√√）
      B 读了消息 → 通知 A（消息已读，√√ 变蓝）
  12. 服务器删除该消息（已成功投递）
```

### 消息回执（已送达 / 已读）

```
√  单勾：消息已到达服务器
√√ 双勾灰：消息已送达接收方设备
√√ 双勾蓝：接收方已读

实现：
  送达回执：B 收到消息后，向服务器发 ACK，服务器通知 A
  已读回执：B 打开聊天页面，发送 "read receipt" 消息给 A
  
  E2EE 下的已读：
    WhatsApp 传的是信令（"B 读了消息 X"），不是内容
    服务器知道读取发生了，但不知道消息内容
```

## 离线消息处理

```
B 手机没开机 / 没有网络：

服务器暂存消息（临时存储，不是永久持久化）
消息保留时间：30 天（超过 30 天未上线，消息丢弃）

B 上线时：
  1. 建立 TLS 长连接
  2. 服务器检测 B 上线
  3. 推送积压的离线消息（按时间顺序）
  4. B 逐一确认（ACK）
  5. 服务器删除已投递的消息

通知提醒：
  B 手机离线时，通过 APNs（iOS）或 FCM（Android）推送通知
  通知内容：只说"你有新消息"，不包含消息内容（E2EE 保护）
  → B 点击通知 → 打开 App → 建立长连接 → 拉取消息
```

## 群消息的 Fanout

```
群 100 人，A 发一条消息：

方案一（Server-side Fanout）：
  服务器给其他 99 人各发一份消息
  压力：服务器端 99 倍写放大
  
方案二（Client-side Fanout，WhatsApp 的选择）：
  A 的手机给每个群成员各加密一份（用每人的公钥）
  发 99 份加密消息到服务器
  服务器只是中继，转发给对应的人
  
  原因：E2EE 要求——服务器不能看到消息，无法统一解密再分发
  代价：大群时客户端需要加密 N 份，发送 N 个包（带宽/CPU 开销大）
  
  群上限：为什么 WhatsApp 群最多 1024 人？
    超过 1024 人，客户端加密 + 发送的开销变得不可接受
```

## 端到端加密（Signal Protocol）

```
WhatsApp 2016 年全面启用 E2EE，使用 Signal Protocol（开源）

核心机制：Double Ratchet（双棘轮）算法

密钥协商（首次通信）：
  A 和 B 各自生成密钥对
  通过 Diffie-Hellman 密钥交换，双方各自推导出相同的共享密钥
  服务器只传递公钥，不存储私钥，无法解密

前向保密（Forward Secrecy）：
  每条消息用不同的临时密钥（Ratchet 向前滚动）
  即使攻击者破解了今天的密钥，也无法解密过去的消息
  
密钥预发布（Prekeys）：
  B 离线时，A 也能发消息
  B 提前把一批"一次性公钥"（One-time Prekeys）上传到服务器
  A 取一个 Prekey，完成密钥协商，发加密消息
  B 上线后用对应的私钥解密
```

## 水平扩展架构

```
早期：单体 Erlang 集群

规模增长后：

[客户端]
    ↓ XMPP over TLS
[Connection Server 集群]（Erlang，每台 200 万连接）
    ↓
[Message Router]（根据接收方 ID 路由到对应 Connection Server）
    ↓
[Offline Storage]（接收方离线时暂存）
    ↓
[Notification Service]（推送 APNs/FCM）

扩展方式：
  Connection Server：无状态（用户连哪台都行），DNS/LB 分配
  路由：维护 userId → connectionServerId 的映射（存 Redis）
  
关键数字：
  2014 年：32 台服务器处理全部消息（Erlang 高效率的体现）
  现在：规模更大，但每台机器的连接密度仍极高
```

## 关键设计决策总结

| 问题 | WhatsApp 的解决方案 | 为什么 |
|------|-------------------|--------|
| 高并发长连接 | Erlang（Actor 模型）| 单台 200 万连接；线程模型做不到 |
| 消息持久化 | 不持久，投递后删除 | 降低存储成本；E2EE 与存储矛盾 |
| 端到端加密 | Signal Protocol（Double Ratchet）| 服务器不能看到消息内容 |
| 群消息 E2EE | 客户端 Fanout（每人一份加密）| 服务器无法统一解密分发 |
| 离线通知 | APNs/FCM（只通知，不含内容）| E2EE 下无法在推送中包含内容 |

---

## 面试可借鉴的点

1. **消息不持久化**——大胆的架构选择，降低存储成本，配合 E2EE 逻辑自洽
2. **Double Ratchet 前向保密**——安全类追问的加分答案
3. **客户端 Fanout（群 E2EE）**——解释群上限 1024 人的设计原因
4. **Erlang Actor 模型**——高并发长连接的极致方案（面试提到即加分）
