# 系统设计面试框架：需求 → 估算 → 架构 → 权衡

## TL;DR

系统设计面试不是考你背方案，而是考你**结构化解决模糊问题的能力**。45 分钟内按这个框架走，每个阶段目标明确：

1. **需求澄清**（5 分钟）：确认边界，避免设计错了方向
2. **容量估算**（5 分钟）：建立数量级感知，指导技术选型
3. **高层架构**（10 分钟）：画出主要组件和数据流
4. **深入设计**（20 分钟）：选 2-3 个核心问题深入
5. **权衡讨论**（5 分钟）：主动总结你的选择和代价

---

## 第一步：需求澄清（5 分钟）

这是最重要的一步，很多人跳过它直接开始设计，结果方向错了。

### 功能需求（Functional Requirements）

澄清系统**要做什么**：

```
题目：设计 Twitter

要问的问题：
- 用户可以发推文（有字数限制吗？）
- 用户可以关注其他用户
- 用户能看到 Timeline（关注的人发的推文）
- 点赞、转发、评论？（这次设计包含吗？）
- 搜索功能？
- 图片/视频？
- 通知？
```

### 非功能需求（Non-Functional Requirements）

澄清系统**要多好**：

```
- 规模：多少用户？多少 QPS？
  "假设 1 亿日活用户"
  
- 可用性：99.9% 还是 99.99%？
  "追求高可用，偶发故障可接受"
  
- 延迟要求：
  "Timeline 加载 < 500ms"
  "发推文延迟可以稍高，< 2s 可接受"
  
- 一致性：
  "发完推文，朋友多久能看到？"
  "最终一致就行，几秒延迟可接受"
  
- 数据规模：
  "数据需要保存多久？"
```

### 澄清的目的

- 确认**核心功能**（不需要什么），把时间花在刀刃上
- 确认**量级**，避免"设计一个支持 100 人的系统"和"支持 1 亿人的系统"用同一套方案
- 确认**一致性和可用性的取舍**，这决定很多技术选型

## 第二步：容量估算（5 分钟）

容量估算的目的不是得出精确数字，而是建立**数量级感知**，从而判断：
- 是否需要缓存
- 是否需要数据库分片
- 存储用什么类型

### 估算框架

**流量：**
```
日活用户 × 每人每天操作次数 = 日请求总量
日请求总量 / 86400秒 = 平均 QPS
峰值 QPS = 平均 QPS × 峰值系数（通常 2-5 倍）
```

**存储：**
```
每条数据大小 × 每天新增数据量 × 保存年限 = 总存储量
```

**带宽：**
```
峰值 QPS × 每次请求的数据大小 = 峰值带宽
```

### 示例：设计 Twitter

```
假设：
  日活用户（DAU）= 1 亿
  每人每天平均发 0.1 条推文（1000万条/天）
  每人每天看 50 条推文

写 QPS：
  1000万 / 86400 ≈ 120 QPS（平均）
  峰值 ≈ 600 QPS（5倍）

读 QPS：
  1亿 × 50 / 86400 ≈ 58000 QPS（平均）
  峰值 ≈ 290000 QPS（5倍）→ 需要缓存！

存储（推文）：
  每条推文 280 字 ≈ 560 字节
  媒体 URL 算 200 字节
  元数据（用户ID、时间戳等）约 100 字节
  合计每条约 1KB

  每天 1000万条 × 1KB = 10GB/天
  5年：10GB × 365 × 5 ≈ 18TB → 需要分布式存储

结论：
  读多写少（58000 : 120 = 480:1）→ 强烈依赖缓存
  写 QPS 不高，无需分片（前期）
  存储量大，需要对象存储或分布式文件系统
```

## 第三步：高层架构（10 分钟）

画出系统的主要组件和数据流，不要陷入细节。

### 标准组件清单

```
[客户端] → [CDN（静态资源）] → [API Gateway（鉴权/限流）]
                                        ↓
                          [负载均衡（Load Balancer）]
                                        ↓
                          [应用服务器（无状态）]
                         /               \
              [缓存（Redis）]        [数据库（MySQL/PostgreSQL）]
                                          ↓
                                   [消息队列（Kafka）]
                                          ↓
                                   [异步处理服务]
```

### 数据流

每个重要的操作，说清楚数据怎么流：

```
用户发推文：
  客户端 → API Gateway（鉴权）→ 推文服务
  → 写入 DB（推文数据）
  → 发消息到 Kafka（"新推文"）
  → 异步：Fanout 服务从 Kafka 消费，把推文推送到关注者的 Timeline 缓存

用户看 Timeline：
  客户端 → API Gateway → Timeline 服务
  → 查 Redis 缓存（Timeline 缓存）
  → Cache Miss → 查 DB 重建 → 写回缓存 → 返回
```

## 第四步：深入设计（20 分钟）

选 2-3 个最核心或最有挑战的问题深入讨论。

### 如何选择深入的点

**面试官引导：** 让面试官指定他最感兴趣的部分
**主动选择：** 选系统中最难的、最有权衡的部分

常见深入点：
- 数据库 Schema 设计
- 缓存策略（如何保证一致性）
- 高并发写入的处理
- 如何实现某个特定功能（如 Fanout、排行榜）

### 深入时的结构

```
1. 说明问题/挑战：
   "Timeline 的主要挑战是：读 QPS 极高（29万 QPS），
    直接查 DB 是不可能的。"

2. 提出方案：
   "我会用 Redis 缓存每个用户的 Timeline，
    最近的 1000 条推文。"

3. 说明实现细节：
   "Timeline 的 Key 是 timeline:{userId}，
    用 Sorted Set，Score 是时间戳，
    Value 是推文 ID。"

4. 说明权衡：
   "这样读取非常快（O(log N) 的 ZRANGE），
    代价是写入时要维护所有关注者的缓存（Fanout），
    大 V 有几千万粉丝时，一条推文要更新几千万个缓存。"

5. 解决新问题：
   "大 V 的推文用拉模式（Pull）：
    用户看 Timeline 时实时查大 V 的最新推文，合并到结果里。
    这叫推拉结合模式。"
```

## 第五步：权衡讨论（5 分钟）

主动总结你的设计决策和代价，展示你对工程权衡的理解。

```
"我们今天设计的系统有几个关键决策：

1. Timeline 用推拉结合
   权衡：写多（Fanout）还是读多（实时拉）
   选择：普通用户用推，大 V 用拉，平衡写入和读取

2. 数据库选 MySQL + Redis
   权衡：一致性（MySQL）vs 性能（Redis）
   选择：推文元数据在 MySQL 保证一致性，热点数据在 Redis

3. 最终一致性
   权衡：发完推文几秒后关注者才看到 vs 强一致但延迟高
   选择：接受几秒延迟，用户体验可接受，换来系统可扩展性

如果时间允许，可以进一步优化：
  - 搜索功能（Elasticsearch）
  - 用户地理位置缓存（降低跨机房延迟）"
```

## 时间管理

| 阶段 | 时间 | 如果面试官打断 |
|------|------|--------------|
| 需求澄清 | 5 min | 接受引导，快速对齐 |
| 容量估算 | 5 min | 可以简化，重要的是展示思路 |
| 高层架构 | 10 min | 先画主流程，细节后补 |
| 深入设计 | 20 min | 跟面试官的兴趣走 |
| 权衡总结 | 5 min | 哪怕被打断也要说出最核心的权衡 |

---

## 常见错误

1. **不澄清需求直接开始画架构**：设计了一个超级复杂的系统，但面试官只想要一个简单的
2. **死背方案，不解释原因**：说"用 Kafka"，但说不出"为什么不用 RabbitMQ"
3. **只展示理想情况**：不提故障处理、不提扩展方案，显示思考不完整
4. **沉默工作**：一边画架构一边不说话，面试官不知道你在想什么，无法评估你的思维
5. **对所有问题都回答"取决于场景"**：有道理但没有立场，好的设计师会给出具体建议
