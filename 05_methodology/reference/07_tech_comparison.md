## 一、消息队列对比

| | **Kafka** | **RabbitMQ** | **AWS SQS** | **Redis Streams** | **Pulsar** |
|--|-----------|--------------|-------------|-------------------|------------|
| **模型** | 分区日志（Log）| 队列（Queue）| 队列 | 分区日志 | 分区日志 + 队列 |
| **吞吐量** | 极高（百万/秒）| 中（万/秒）| 高（托管无上限）| 高（受内存限制）| 极高 |
| **延迟** | 低（毫秒级）| 极低（亚毫秒）| 中（毫秒~秒）| 极低 | 低 |
| **消息保留** | 长期保留（可回放）| 消费后删除 | 消费后删除（最长 14 天）| 可配置（内存/磁盘）| 长期（分层存储）|
| **消费模式** | Pull（消费者主动拉）| Push（Broker 推）| Pull | Pull + Push | Pull + Push |
| **顺序保证** | 分区内有序 | 队列内有序 | 标准队列不保证；FIFO 队列保证 | 分区内有序 | 分区内有序 |
| **Exactly-Once** | 支持（幂等生产者 + 事务）| 不原生支持 | 不支持（At-least-once）| 不原生支持 | 支持 |
| **运维复杂度** | 高（需要 ZooKeeper/KRaft）| 中 | 低（全托管）| 低（Redis 自带）| 高 |
| **适合场景** | 日志、事件流、审计、数据管道 | 任务队列、RPC、复杂路由 | 云原生解耦、简单队列 | 轻量事件流、已有 Redis | 多租户、跨地域、云原生 |
| **决定性理由** | 需要**回放历史消息**或**极高吞吐** | 需要**复杂路由**（Exchange/Binding）或**任务优先级** | 不想运维、**纯 AWS 生态** | 已经在用 Redis、**不想引入新组件** | 需要**多租户**隔离或**跨地域复制** |

**面试选型口诀：**
```
日志/审计/数据管道 → Kafka
任务队列/优先级/复杂路由 → RabbitMQ
纯 AWS 无脑省事 → SQS
轻量/已有 Redis → Redis Streams
```

## 二、数据库对比

### 2a. 关系型

| | **MySQL** | **PostgreSQL** |
|--|-----------|---------------|
| **擅长** | 高并发读写、简单查询 | 复杂查询、JSON、全文搜索、地理空间 |
| **JSON 支持** | 基础 | 原生 JSONB（可索引）|
| **复制** | 主从（Binlog）| 主从（WAL Streaming）|
| **扩展性** | 分片成熟（Vitess）| 分片稍弱（Citus）|
| **选它** | 互联网高并发 CRUD | 复杂业务逻辑、需要 JSONB 或地理查询 |

### 2b. NoSQL 全家桶

| | **Redis** | **Cassandra** | **MongoDB** | **DynamoDB** | **Elasticsearch** | **ClickHouse** |
|--|-----------|--------------|-------------|--------------|-------------------|----------------|
| **类型** | KV / 数据结构 | 宽列 | 文档 | KV / 文档 | 全文搜索引擎 | 列式 OLAP |
| **CAP** | CP（单机）/ AP（Cluster）| AP | CP（默认）| AP（默认）| AP | AP |
| **写吞吐** | 极高 | 极高（LSM Tree）| 高 | 极高（托管）| 中 | 高（批量）|
| **读延迟** | 亚毫秒 | 低毫秒 | 低毫秒 | 低毫秒（单位 ms）| 毫秒~百毫秒 | 秒级（大查询）|
| **持久化** | 可选（RDB/AOF）| 强（多副本）| 强 | 强（托管）| 强 | 强 |
| **查询能力** | 简单 KV / 结构操作 | 限定主键/索引 | 富查询（聚合管道）| 限定主键/GSI | 全文 + 聚合 | 复杂 OLAP SQL |
| **扩展方式** | 垂直 / Cluster 分片 | 原生水平分片 | 分片 | 自动（托管）| 分片 | 分片 |
| **适合场景** | 缓存、会话、计数器、排行榜、分布式锁 | 时序数据、物联网、用户行为日志 | 灵活 Schema 的业务数据 | 无运维、AWS 生态的高并发 KV | 全文搜索、日志分析 | 实时报表、用户分析、广告统计 |
| **决定性理由** | **极低延迟**或**内存数据结构**（ZSet/HyperLogLog）| **极高写入** + **时间序列** + **多地域**天然支持 | **灵活 Schema** + 复杂文档查询 | **零运维** + AWS 原生 | **全文检索**或**日志聚合** | **OLAP 分析**（列式压缩，聚合极快）|

**面试选型速查：**
```
缓存 / 会话 / 排行榜          → Redis
用户行为日志 / IoT / 写入密集  → Cassandra
文档型业务数据 / 灵活 Schema   → MongoDB
全文搜索 / 日志分析            → Elasticsearch
实时 OLAP / 广告统计           → ClickHouse
纯 AWS 无运维                  → DynamoDB
```

## 三、缓存策略对比

| 策略 | 读流程 | 写流程 | 一致性 | 适合场景 | 缺点 |
|------|--------|--------|--------|---------|------|
| **Cache-Aside（旁路）** | 先读缓存，Miss 时读 DB 并回填 | 写 DB，**删除**（或更新）缓存 | 最终一致（短暂不一致窗口）| 读多写少，最常用 | 冷启动 Miss 多；并发写可能脏缓存 |
| **Write-Through（写穿）** | 先读缓存，Miss 读 DB | **同时写缓存和 DB**（同步）| 强一致 | 读写都要快、不能容忍不一致 | 写放大；不常读的数据也占缓存 |
| **Write-Back（写回）** | 先读缓存，Miss 读 DB | **只写缓存**，异步批量刷 DB | 最终一致（缓存是 Source of Truth）| 写密集型、可容忍少量丢失 | 缓存故障可能丢数据 |
| **Write-Around（绕写）** | 先读缓存，Miss 读 DB | **只写 DB**，不写缓存 | 最终一致 | 写多读少（避免缓存污染）| 首次读必然 Miss，冷数据延迟高 |
| **Read-Through** | 缓存代理读 DB（应用只访问缓存）| 应用只写缓存（缓存负责同步）| 依赖实现 | 简化应用层逻辑 | 缓存层复杂，调试难 |

**关键区别记忆：**
```
Cache-Aside：应用自己管缓存，最灵活，最常见
Write-Through：写时两边都更新，一致性最好，写慢
Write-Back：只写缓存，性能最好，有丢数据风险
Write-Around：写绕过缓存，适合"写了不怎么读"的数据
```

**缓存三大问题：**

| 问题 | 触发场景 | 解决方案 |
|------|---------|---------|
| **缓存穿透** | 查询不存在的 key，每次都打 DB | 布隆过滤器拦截；或缓存空值（TTL 短）|
| **缓存击穿** | 热点 key 过期的瞬间，大量请求打 DB | 互斥锁（只让一个请求回源，其余等待）；或永不过期 + 异步更新 |
| **缓存雪崩** | 大批 key 同时过期，或缓存整体宕机 | TTL 加随机 jitter；多级缓存；熔断降级 |

## 四、通信协议对比

| | **REST** | **gRPC** | **GraphQL** | **WebSocket** | **SSE** |
|--|----------|----------|-------------|---------------|---------|
| **协议** | HTTP/1.1+（文本）| HTTP/2（二进制）| HTTP（文本）| TCP 长连接 | HTTP 长连接（单向）|
| **方向** | 请求-响应 | 请求-响应 / 流 | 请求-响应 | 全双工 | 服务端推 |
| **数据格式** | JSON（人类可读）| Protobuf（紧凑二进制）| JSON | 任意 | 文本事件流 |
| **性能** | 中 | 高（体积小、多路复用）| 中 | 高（持久连接）| 中 |
| **强类型** | 无（需 OpenAPI）| 是（.proto 文件）| 是（Schema）| 无 | 无 |
| **流式支持** | 否（需 Polling）| 是（双向流）| Subscription | 是 | 是（单向）|
| **浏览器支持** | ✅ | 需要 grpc-web | ✅ | ✅ | ✅ |
| **适合场景** | 公开 API、移动端、简单服务间调用 | 微服务内部调用、低延迟高吞吐 | 复杂前端查询、移动端按需取数 | 实时双向（聊天、游戏、协同）| 服务端推（通知、股票行情、日志流）|
| **决定性理由** | **通用性最好**，所有客户端都支持 | **微服务内部**，性能和强类型双收益 | **前端驱动**，避免 Over/Under-fetching | **需要服务端主动推**且客户端也要发消息 | **只需服务端推**，比 WebSocket 更简单 |

## 五、负载均衡算法对比

| 算法 | 原理 | 优点 | 缺点 | 适合场景 |
|------|------|------|------|---------|
| **轮询（Round Robin）** | 依次分配 | 简单均匀 | 不考虑服务器负载差异 | 无状态、同质服务器 |
| **加权轮询** | 按权重比例分配 | 适配异构服务器 | 权重需手动维护 | 服务器配置不同 |
| **最少连接** | 分给当前连接数最少的 | 适应负载波动 | 新节点会被瞬间打满 | 长连接（WebSocket、DB 连接）|
| **IP Hash** | 客户端 IP 取模 | 同一用户固定路由 | NAT 后流量不均 | 需要 Sticky Session |
| **随机** | 随机选择 | 极简 | 可能不均 | 同质节点、低流量 |
| **一致性哈希** | 哈希环，key 映射到最近节点 | 扩缩容时迁移量小 | 实现复杂 | 分布式缓存（Redis Cluster）|

## 六、存储类型对比

| | **块存储（Block）** | **文件存储（File）** | **对象存储（Object）** |
|--|---------------------|---------------------|----------------------|
| **访问方式** | 原始数据块（挂载为磁盘）| 文件路径（NFS/SMB）| HTTP API（S3 API）|
| **结构** | 无结构 | 目录树 | 扁平（Bucket + Key）|
| **延迟** | 极低（微秒）| 低（毫秒）| 中（毫秒~百毫秒）|
| **容量** | TB 级 | TB~PB 级 | PB~EB 级（近乎无限）|
| **修改能力** | 随机读写 | 随机读写 | 不可原地修改（覆写整个对象）|
| **适合存** | 数据库数据文件、VM 磁盘 | 共享文件、代码仓库 | 图片、视频、备份、日志、静态资源 |
| **代表产品** | AWS EBS、GCP Persistent Disk | AWS EFS、NAS | AWS S3、GCS、Azure Blob |
| **决定性理由** | 数据库需要**低延迟随机 IO** | 多机器需要**共享访问同一文件** | **海量非结构化数据**、按需付费、不需要修改 |

## 七、一致性模型速查

| 级别 | 保证 | 代价 | 典型实现 | 适合场景 |
|------|------|------|---------|---------|
| **线性一致性（Linearizability）** | 操作瞬间原子生效，全局有序 | 最高延迟 | ZooKeeper、etcd、Raft | 分布式锁、Leader 选举 |
| **顺序一致性** | 所有进程看到相同操作顺序 | 高延迟 | 少用 | 理论模型 |
| **因果一致性** | 因果相关的操作有序，并发操作可乱序 | 中等 | MongoDB Causal Session | 社交评论、帖子 |
| **Read-Your-Writes** | 自己写的立刻能读到 | 低（只保证单用户）| 主库读 / Session 一致性 | 用户更新个人资料后刷新页面 |
| **最终一致性** | 最终会收敛，过程中可以不一致 | 最低 | Cassandra（AP）、DNS、CDN | 点赞数、搜索索引、Feed |
