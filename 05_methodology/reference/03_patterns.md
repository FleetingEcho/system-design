# 常见设计模式：读写分离 / CQRS / Fanout / Event Sourcing

## TL;DR

这四个模式在 case studies 里反复出现。理解它们的本质（解决什么问题、代价是什么），而不是死记做法。

---

## 读写分离（Read/Write Splitting）

### 问题

单库既要处理写入（INSERT/UPDATE），又要处理大量读取（SELECT），读写互相竞争资源，在高并发时成为瓶颈。

### 解决方案

```
写请求 → 主库（Master）
读请求 → 从库（Replica 1, 2, 3...）

主库把数据通过 Binlog 同步到从库
```

### 代价

- **复制延迟**：写完主库到从库同步完成有时间差（通常毫秒级，高峰可能秒级）
- **读己写一致性**：用户刚写入的数据，立即从从库读可能读不到
- **故障转移**：主库宕机需要时间提升从库，期间写操作不可用

### 适用场景

读多写少的系统（绝大多数互联网产品）。读写比超过 5:1 时就值得考虑。

### 与 CQRS 的区别

读写分离是**数据库层面**的分离（两个库，相同 Schema）。CQRS 是**应用层面**的分离（读模型和写模型完全不同）。

---

## CQRS（Command Query Responsibility Segregation）

### 问题

写模型和读模型往往形状不同：
- 写：关注数据完整性，需要事务
- 读：关注查询效率，经常需要聚合多张表

用一个模型同时服务两者，要么写复杂，要么读复杂。

### 解决方案

把写操作（Command）和读操作（Query）分离成**独立的模型**：

```
写路径：
  客户端 → Command（CreateOrder, UpdateUser）
         → 写模型（规范化的主存储，MySQL）
         → 发出事件（OrderCreated, UserUpdated）
         → 异步更新读模型

读路径：
  客户端 → Query（GetOrderList, SearchUsers）
         → 读模型（反范式的查询优化存储，Elasticsearch / Redis / 特殊宽表）
```

### 例子：订单列表查询

**写模型（规范化，3NF）：**
```sql
orders: (id, user_id, status, created_at)
order_items: (order_id, product_id, quantity, price)
products: (id, name, category)
```

**读模型（反范式，针对查询优化）：**
```json
{
  "orderId": "1001",
  "userId": "u001",
  "status": "completed",
  "productNames": ["iPhone 15", "AirPods"],
  "totalAmount": 8999,
  "createdAt": "2024-01-01"
}
```

读模型是预聚合的，查一次就够，不需要 JOIN。

### 代价

- **数据同步延迟**：读模型是异步更新的，可能有短暂不一致
- **实现复杂度**：维护两套模型，写逻辑要负责触发读模型更新
- **数据冗余**：同一数据存了两份

### 适用场景

- 读写模式差异大（读需要大量 JOIN 聚合，写需要严格事务）
- 读 QPS 远高于写（读模型可以专门优化）
- 需要多种读取视角（同一数据对不同消费者展示不同形态）

## Fanout（扇出）

### 问题

一条内容（如推文、消息）产生后，需要发送给所有关注者 / 群成员 / 订阅者。如何高效地"一对多"分发？

### 两种策略

**推模式（Fanout on Write / Push）：**

```
用户A 发推文
  ↓
Fanout 服务：拉取用户A 的所有粉丝列表
  ↓
把推文 ID 写入每个粉丝的 Timeline 缓存
（1000万粉丝 = 写 1000万个缓存条目）

用户 B 读 Timeline：
  直接读自己的缓存，速度极快
```

**优点：** 读极快（预计算）
**缺点：** 写代价极高（大 V 有 1000 万粉丝，一条推文要写 1000 万次）

**拉模式（Fanout on Read / Pull）：**

```
用户A 发推文
  ↓
只写一次：保存推文到推文库

用户B 读 Timeline：
  查询所有关注的人（B 关注了 50 人）
  获取这 50 人最新的推文
  实时合并排序
```

**优点：** 写极快（只写一次）
**缺点：** 读慢（每次都要查 50 个人的推文然后合并）

**推拉结合（Twitter 的实际做法）：**

```
普通用户（粉丝 < 1 万）→ 推模式：一发推文就 Fanout 到粉丝 Timeline
大 V（粉丝 > 1 万）→ 拉模式：用户读 Timeline 时实时拉取大 V 的最新推文

读 Timeline：
  缓存里的 Timeline（来自普通用户的推文）
  + 实时拉取关注的大 V 的最新推文
  → 合并后返回
```

### 适用场景

所有"一对多广播"的场景：
- 社交媒体 Timeline（推文、帖子）
- 消息通知（一个事件通知多个服务）
- 群聊（一条消息送达所有群成员）

## Event Sourcing（事件溯源）

### 问题

传统数据库存的是**当前状态**：

```
账户表：id=1, balance=100
```

你只知道现在余额是 100，不知道发生了什么。如果需要审计日志、时间旅行（回到某个历史状态）、或者从事件重放来更新读模型，传统方案很难。

### 解决方案

不存当前状态，只存**事件（Event）**：

```
事件日志：
  [账户已创建: id=1, initialBalance=0]
  [资金已存入: id=1, amount=200, at=T1]
  [资金已取出: id=1, amount=100, at=T2]
  [资金已存入: id=1, amount=0, at=T3]

当前状态 = 重放所有事件：
  0 + 200 - 100 + 0 = 100（这就是当前余额）
```

### 优点

- **完整审计日志**：所有变更都有记录，不会丢失历史
- **时间旅行**：重放到任意时间点的状态
- **事件驱动**：事件可以触发其他系统的响应
- **Bug 修复**：发现程序 Bug 后，可以修正 Bug 重放历史事件，得到正确状态

### 缺点

- **查询复杂**：获取当前状态需要重放所有事件，需要**快照（Snapshot）**定期保存当前状态减少重放量
- **存储增长**：事件永不删除，存储持续增长
- **实现复杂**：需要配套的 CQRS（读模型单独维护）

### 适合场景

- 金融系统（账户变动必须有完整审计轨迹）
- 电商订单（订单状态变更的完整历史）
- 协同编辑（每次编辑都是事件，支持撤销/重做）
- 复杂领域（Domain Event 是领域驱动设计 DDD 的核心）

**不适合：**
- 简单 CRUD（Over-engineering）
- 对查询性能要求极高且历史不重要的场景

## 四个模式的关系

```
读写分离：数据库层面分离，解决单库读写竞争
    ↓（更激进）
CQRS：应用层面分离，读模型和写模型完全不同
    ↓（读模型的更新方式）
Event Sourcing：用事件日志作为 Source of Truth，驱动 CQRS 的读模型
    ↓（一事件多消费者）
Fanout：一个事件广播给多个下游系统/用户
```

这四个模式经常组合使用：Event Sourcing 产生事件 → Fanout 分发事件 → 各消费者更新各自的 CQRS 读模型。

---

## 面试中如何应用这些模式

| 场景 | 推荐模式 |
|------|---------|
| 读 QPS 远高于写 | 读写分离 |
| 读需要大量聚合，写需要严格事务 | CQRS |
| 社交 Feed、群聊 | Fanout（推拉结合）|
| 需要审计、事件回放 | Event Sourcing |
| 实时数据管道 | Event Sourcing + 消息队列（Kafka）|
