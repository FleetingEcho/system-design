# 系统设计面试套路总结

## TL;DR

这篇文档是所有 case study 的"元模板"，帮你把任何新题目都能拆解成标准流程。面试前读这篇，胜过临时背 10 个具体系统。

---

## 通用设计流程（45 分钟分配）

```
[0-5min]   需求澄清：功能边界 + 规模
[5-10min]  容量估算：QPS + 存储 + 带宽
[10-20min] 高层架构：核心组件 + 数据流
[20-40min] 深入设计：2-3个核心难点
[40-45min] 总结权衡：选择 + 代价 + 未来优化
```

## 每类系统的核心考点

### 存储密集型（YouTube、Dropbox、S3）

**必谈点：**
- 上传流程（分片上传、断点续传）
- 存储选型（对象存储 vs 文件系统）
- 读取加速（CDN）
- 去重（内容寻址，SHA256 做 Key）

**关键问题：** "大文件怎么上传？""用户怎么快速下载全球各地的文件？"

---

### 消息/聊天系统（WhatsApp、Slack、微信）

**必谈点：**
- 在线推送（WebSocket 持久连接）
- 离线消息（存储 + 上线后拉取）
- 消息顺序保证（单会话内有序）
- 已读/未读状态

**关键问题：** "用户 A 和用户 B 消息的顺序如何保证？""离线的用户如何收到消息？"

---

### Feed 流（Twitter、微博、朋友圈）

**必谈点：**
- 推拉模式（Fanout on Write vs Read）
- 大 V 问题（几千万粉丝的推拉结合）
- Timeline 缓存（Redis Sorted Set）
- 发布延迟可接受（最终一致）

**关键问题：** "用户的 Feed 怎么生成？""大 V 发帖后所有粉丝能立刻看到吗？"

---

### 搜索系统（Google、微信搜索、ElasticSearch）

**必谈点：**
- 爬取/索引建立（异步）
- 倒排索引（Inverted Index）
- 排名算法（简述 PageRank / TF-IDF）
- 搜索自动补全（Trie / 前缀索引）
- 主存储 + 搜索引擎同步

**关键问题：** "搜索是实时的吗？新内容多久能被搜到？"

---

### 限流 / 防刷系统

**必谈点：**
- 限流算法选型（令牌桶 vs 漏桶）
- 分布式计数器（Redis）
- 限流维度（IP / 用户 / API Key）
- 限流后的行为（返回 429 + Retry-After）

**关键问题：** "多台服务器如何共享限流状态？""如何防止边界效应？"

---

### 通知系统（推送、邮件、短信）

**必谈点：**
- 多渠道（Push / Email / SMS / In-App）
- 优先级队列（紧急通知先发）
- 重试 + 幂等（不重复发送）
- 用户偏好（Do Not Disturb 时间段）

**关键问题：** "如何保证重要通知不丢失？""如何防止同一通知发两次？"

---

### 打车/地图系统（Uber、滴滴）

**必谈点：**
- 地理索引（Geohash / QuadTree）
- 实时位置更新（高频写入，Cassandra）
- 司机匹配算法（简述）
- 行程状态机（订单状态转换）

**关键问题：** "如何找到附近的司机？""位置每秒更新如何处理高频写入？"

---

### URL 短链接 / 二维码

**必谈点：**
- Hash 算法（Base62）
- 冲突处理
- 重定向（301 vs 302）
- 过期和删除策略

**关键问题：** "如何保证短码全球唯一？""301 和 302 有什么区别，对分析数据有影响吗？"

---

### 分布式缓存（Redis Cluster、Memcached）

**必谈点：**
- 一致性哈希（扩缩容时数据迁移）
- 缓存淘汰策略（LRU / LFU）
- 缓存穿透/击穿/雪崩
- 持久化选项

**关键问题：** "加减节点时数据怎么迁移？""如何处理热点数据？"

## 高频决策与标准答案

### "数据库用什么？"

```
有关系 + 需要事务 → MySQL / PostgreSQL
写多读少 + 大数据量 → Cassandra
高 QPS 读 + 简单查找 → Redis
全文搜索 → Elasticsearch（配合主数据库）
用户行为日志 → HBase / ClickHouse
文件/图片 → 对象存储（S3）
```

### "如何处理高并发读？"

```
1. 加缓存（Redis Cache-Aside）
2. CDN（静态资源）
3. 读写分离（从库承担读）
4. 数据分片（如果单库撑不住）
```

### "如何处理高并发写？"

```
1. 消息队列削峰（异步处理）
2. 批量写入
3. 数据库分片
4. NoSQL（Cassandra 写入极快）
```

### "如何保证系统高可用？"

```
1. 消除单点故障（每个组件多实例）
2. 负载均衡
3. 熔断器（下游故障时快速失败）
4. 多机房部署
5. 数据异地备份
```

### "如何保证数据不丢失？"

```
1. 数据库持久化（WAL）
2. 主从复制（异地容灾）
3. 消息队列持久化（Kafka 落盘）
4. 定期备份
```

## 万能的架构模板

几乎所有系统都包含这些组件，按需取用：

```
[移动/Web 客户端]
        ↓
    [CDN（静态资源）]
        ↓
  [DNS 负载均衡]
        ↓
  [API Gateway（鉴权/限流/路由）]
        ↓
  [Load Balancer]
        ↓
[无状态应用服务器集群]
    /         |         \
[缓存层]  [主数据库]  [消息队列]
(Redis)  (MySQL/PG) (Kafka)
              |           |
         [从数据库]  [异步处理服务]
                         |
                   [搜索索引]
                   [对象存储]
                   [分析数据库]
```

## 面试中的加分项

1. **主动讨论监控和可观测性**："我们需要监控 P99 latency、错误率、消息队列 lag，在这些指标超出 SLO 时告警。"

2. **说出数字**："单台 MySQL 大约能抗 1 万 QPS，我们预期 5 万 QPS，所以需要 5 台从库或者分片。"

3. **提出未来扩展点**："当前设计支持 1000 万用户，如果增长到 1 亿用户，Timeline 缓存会撑不住，到时候需要引入大 V 的拉模式。"

4. **承认选择的代价**："用最终一致性牺牲了强一致，意味着用户发帖后关注者最多有几秒的延迟才能看到，这对于社交产品是可接受的。"
