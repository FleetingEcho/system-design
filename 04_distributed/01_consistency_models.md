# 一致性模型：强一致性 / 最终一致性 / 因果一致性

## TL;DR

- **线性一致性（Linearizability）**：最强，操作像单机一样原子，是分布式锁的基础
- **因果一致性（Causal Consistency）**：有因果关系的操作保序，无因果关系的可以乱序
- **最终一致性（Eventual Consistency）**：只保证最终收敛，过程不一致，是大多数 NoSQL 的选择
- **可调一致性（Tunable Consistency）**：Cassandra/DynamoDB 的做法，用 W+R>N 控制强度

---

## 为什么需要多种一致性模型

强一致性代价极高——写入时要等所有副本确认，延迟是所有副本中最慢的那个。在跨机房、跨地域场景下，强一致性意味着每次写入要等 150ms+ 的跨洲延迟。

**现实是：不同数据对一致性的要求不同。**

- 银行账户余额：必须强一致，差一分钱都不行
- 社交媒体点赞数：差几个完全可以接受
- 用户个人资料：几秒内同步就够了

不同的一致性模型，就是为不同数据量身定制的保证级别。

---

## 线性一致性（Linearizability）

### 精确定义

线性一致性是最强的一致性模型。它要求：

> 所有操作看起来都是**瞬间原子执行**的，且顺序与真实时间顺序一致。

换句话说：一旦一个写操作完成（客户端收到"成功"响应），**任何后续**的读操作（任何客户端，任何节点），都必须能看到这次写入的值。

```
时间线：
t=0  Client1: write(x=2)
t=1  Client1: 收到"写入成功"
t=2  Client2: read(x) → 必须返回 2（不能返回旧值）
t=3  Client3: read(x) → 必须返回 2
```

### 线性一致性的实现

实现线性一致性需要在多个副本之间达成共识：
- 单主复制（Leader-based）：所有写入经过主节点，主节点确认后才返回
- 多数派（Quorum）：多数节点确认后才返回（W + R > N）
- 分布式共识算法（Raft/Paxos）：确保所有节点对操作顺序达成一致

### 线性一致性的代价

- **延迟**：必须等多数节点响应，延迟 = max(所有参与节点延迟)
- **可用性**：节点故障或网络分区时，可能无法达到多数派，拒绝请求

### 适用场景

- **分布式锁**：必须是线性一致的，否则两个客户端可能同时认为自己持有锁
- **Leader 选举**：整个集群必须对"谁是 Leader"达成一致
- **唯一约束**：用户名不能重复，需要线性一致的读后写操作

---

## 顺序一致性（Sequential Consistency）

比线性一致性弱一点：操作有全局顺序，但不要求与真实时间对齐。

```
线性一致：time(op1) < time(op2) → op1 在全局顺序中先于 op2
顺序一致：不要求，只要所有进程看到的顺序一致就行
```

实践中顺序一致性很少单独提，大多数系统要么是线性一致，要么更弱。

---

## 因果一致性（Causal Consistency）

### 精确定义

有**因果关系**的操作，所有节点看到的顺序必须一致。无因果关系的并发操作，不同节点可以有不同的顺序。

**因果关系：**
```
A 先发帖，B 看到帖子后评论
→ A 的发帖 和 B 的评论 有因果关系
→ 任何人看到 B 的评论，就一定也能看到 A 的帖子
```

```
A 在上海改了个人资料
B 在纽约同时改了个人资料（两者互不知情）
→ 两个操作无因果关系（并发）
→ 不同节点可以先看到 A 的改动也可以先看到 B 的改动
→ 最终都会看到两个改动
```

### 向量时钟（Vector Clock）

因果一致性的实现需要追踪因果关系，常用**向量时钟**：

```
每个节点维护一个向量，记录它"见过"的每个节点的最新操作版本：

初始状态：A=[0,0,0], B=[0,0,0], C=[0,0,0]（3个节点）

节点A发生操作：A=[1,0,0]
节点A把结果同步给B：B=[1,0,0]
节点B在收到A的操作后发生操作：B=[1,1,0]
→ B=[1,1,0] 说明"我见过A的第1个操作，自己发生了第1个操作"

节点C没有同步，自己发生操作：C=[0,0,1]
→ C=[0,0,1] 说明"我没见过A或B的操作，自己发生了第1个操作"

B的操作和C的操作：
  B=[1,1,0]，C=[0,0,1]
  → 无法比较大小（互不知道对方）→ 并发操作，无因果关系
  → 合并时可能有冲突

B同步给A后，A收到B的[1,1,0]：
  A之前是[1,0,0]，现在看到B已经[1,1,0]
  → A知道B的操作发生在A的操作之后（因为B知道A的第1个操作）
```

### 因果一致性的适用场景

- 社交媒体（"先看到帖子，才能看到评论"）
- 协同编辑（操作依赖顺序）
- 消息系统（用户B的回复必须在用户A的消息之后）

## 最终一致性（Eventual Consistency）

### 精确定义

> 如果停止写入，经过足够时间，所有副本的数据会最终收敛到相同的值。

这是最弱的一致性保证，只承诺"最终"，不承诺过程中的任何一致性。

```
写入操作完成后：
  节点1：x=2（新值，立即看到）
  节点2：x=1（旧值，同步中）
  节点3：x=2（新值，快）
  
一段时间后（同步完成）：
  节点1：x=2
  节点2：x=2  ← 同步完成
  节点3：x=2
```

### 最终一致性的变体

**读己写一致性（Read-Your-Writes）：**
用户总是能看到自己写入的数据（但可能看不到别人的最新写入）。
```
用户修改昵称 → 立刻自己可以看到新昵称
其他用户 → 可能还看到旧昵称（几秒后同步）
```

**单调读一致性（Monotonic Read）：**
用户不会看到数据"变旧"——如果读到了 x=2，下次读不会读到 x=1。

**单调写一致性（Monotonic Write）：**
同一个客户端的写操作按顺序执行，不会乱序。

## 可调一致性（Tunable Consistency）

Cassandra 和 DynamoDB 允许在每次操作时指定一致性级别，用 Quorum 数学控制：

### Quorum 读写

```
N = 副本总数（例如 3）
W = 写入需要确认的副本数
R = 读取需要查询的副本数

保证强一致性：W + R > N
```

**常见配置：**

```
N=3 的集群：

W=1, R=1（最低延迟，最终一致）：
  写入1个副本就返回，读取1个副本
  W+R=2 < N=3，可能读到旧数据

W=2, R=2（Quorum，强一致）：
  写入2个副本才返回，读取2个副本取最新
  W+R=4 > N=3，读一定能看到最新写入

W=3, R=1（写强一致，读任意）：
  写入所有副本才返回（延迟高）
  读1个就行（因为所有副本都是最新的）

W=1, R=3（写快，读强一致）：
  写入1个副本快速返回
  读3个副本取最新（会看到最新写入）
```

**Cassandra 的一致性级别：**

```
ONE    → W=1 或 R=1（最低延迟）
QUORUM → W=N/2+1 或 R=N/2+1（强一致）
ALL    → W=N 或 R=N（最高延迟，最强一致）
LOCAL_QUORUM → 只在本地数据中心达到多数派（跨数据中心可以弱一致）
```

## 冲突解决

当两个副本上的同一条数据被并发修改，合并时产生冲突，需要解决：

### Last-Write-Wins（LWW，最后写入获胜）

用时间戳决定，时间戳更大的值获胜：

```
副本1：x=2，时间戳=100
副本2：x=3，时间戳=99
→ 合并后：x=2（时间戳100更大）
```

**问题：** 分布式系统中时钟不完全同步（时钟漂移），时间戳不能完全信任，可能丢失合法写入。

### CRDT（Conflict-free Replicated Data Types）

设计特殊数据结构，使任意顺序合并都能得到确定且正确的结果：

**G-Counter（只增计数器）：**
```
每个节点维护自己的计数，合并时取各节点最大值
节点A：[5, 0, 0]（A自己增了5次）
节点B：[0, 3, 0]（B自己增了3次）
合并：[5, 3, 0]，总数=5+3=8
```

**G-Set（只增集合）：**
合并就是求并集，无冲突

**LWW-Register：**
LWW 的数据结构化版本，每个字段有时间戳

CRDT 的典型应用：Google Docs 的实时协作（文档是 CRDT 数据结构，任意节点的修改都可以合并）

### 向量时钟 + 人工/应用层解决

记录所有冲突版本，由应用层（或用户）选择合并策略：

Amazon DynamoDB 用这种方式——冲突时同时保留多个版本，由应用层决定取哪个。

## 与 Node.js/TS 生态的类比

你用 Prisma 连 PostgreSQL 时，享受的是强一致性（单机情况下）：

```typescript
// 这个操作是线性一致的：
await prisma.account.update({ where: { id: 1 }, data: { balance: 100 } });
// 立刻之后：
const account = await prisma.account.findUnique({ where: { id: 1 } });
// account.balance 一定是 100（不是旧值）
```

你用 Redis 做缓存时，接受的是最终一致性：
```typescript
// 写 DB（强一致）
await prisma.user.update({ where: { id: 1 }, data: { name: 'Bob' } });
// 异步更新缓存（最终一致，可能有延迟）
await redis.set('user:1', JSON.stringify({ name: 'Bob' }));
// 在这两行之间，其他服务读缓存可能还看到旧名字
```

## 常见陷阱

1. **把"最终一致"理解成"数据可以丢"**：最终一致性的系统设计好了数据不会丢，只是不同节点暂时看到不同的值
2. **在需要线性一致的场景用了最终一致**：分布式锁用了最终一致的存储，导致两个节点同时认为自己持有锁（脑裂）
3. **LWW 在时钟漂移时丢数据**：节点时钟差几毫秒，合法写入被"旧时钟"覆盖，用向量时钟更安全
4. **Quorum 没有考虑节点宕机**：N=3, W=2，一台机器宕机，只剩 2 台，W=2 仍然可以写（2>=2），但 R=2 读取时必须都返回成功，没有容错空间

## 面试常见问答

### 简单

**Q：强一致性和最终一致性的区别是什么？**

A：强一致性（具体是线性一致性）保证：写操作完成后，任何后续读操作都能立即看到新值，不存在读到旧数据的窗口。最终一致性保证：写操作完成后，数据会在多个副本间传播，最终所有副本会有相同的值，但传播期间不同副本可能有不同的值。强一致性代价是延迟高和可用性下降；最终一致性代价是可能读到旧数据，但延迟低可用性高。

---

**Q：什么是读己写一致性？为什么这个很重要？**

A：读己写一致性（Read-Your-Writes）是指：用户写入数据后，自己的后续读操作一定能看到刚才写入的数据。这对用户体验非常重要——用户刚修改了密码，立刻登录，却因为读到了旧密码被拒绝，会非常困惑。实现方式：用户有写操作后，其读请求路由到主库（而不是从库）；或者记录用户最新写入的时间戳，读取时确保从库已同步到该时间戳。

---

### 中等

**Q：Cassandra 的 QUORUM 一致性级别是什么？W + R > N 是什么意思？**

A：Quorum 读写是 Cassandra 实现强一致性的方式。N 是副本总数，W 是写入需要等待确认的副本数，R 是读取需要查询的副本数。W + R > N 保证：写入的多数节点和读取的多数节点之间**必然有交集**，读操作一定能读到最新的写入。例如 N=3, W=2, R=2：写入时等 2 个副本确认，读取时查 2 个副本取最新。因为 2+2=4>3，两个集合至少有 1 个共同节点，该节点有最新数据。降低 W 或 R 可以提高性能，但 W+R≤N 时就是最终一致性。

---

### 难

**Q：什么是 CRDT？举一个实际的例子说明它如何解决并发冲突。**

A：CRDT（Conflict-free Replicated Data Type）是一类特殊设计的数据结构，数学上保证任意顺序、任意次数的合并都能得到相同的确定结果，从而无需协调就能解决并发冲突。

实际例子——**协同文档中的文字插入：**

普通方式下两个用户同时插入字符会冲突：
```
初始文本：Hello
User A 在位置3插入"X"：HelXlo
User B 在位置3插入"Y"：HelYlo
两个操作同时发生，合并时哪个在前？
```

用 RGA（Replicated Growable Array）CRDT：
```
每个字符有唯一 ID（节点ID + 时间戳）
用户A插入的"X"的 ID = (A, t=10)
用户B插入的"Y"的 ID = (B, t=10)
合并规则：ID 更大的排在前面（B > A 按字母序）
合并结果：HelYXlo（所有节点合并后都得到这个结果）
```

这就是 Google Docs、Figma 等协同编辑工具底层数据结构的核心思想。结果"正确性"是数学保证的，不依赖网络传输顺序。
