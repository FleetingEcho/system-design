# CAP 定理

## TL;DR

分布式系统无法同时满足以下三点，**最多只能满足其中两个**：
- **C**onsistency（一致性）：所有节点在同一时刻看到相同的数据
- **A**vailability（可用性）：每个请求都能收到响应（不保证是最新数据）
- **P**artition tolerance（分区容忍性）：网络出现分区（节点间通信中断）时系统仍能工作

**实际结论**：网络分区在真实分布式系统中必然会发生，P 是必须保留的。因此真正的选择是 **CP 还是 AP**。

---

## 什么是分布式系统中的"节点分区"

网络分区（Network Partition）是指：分布式系统中，部分节点之间的网络连接断开了，导致整个集群被"切割"成两个或多个无法互相通信的子集。

```
正常状态：
Node A ←——→ Node B ←——→ Node C

分区后：
Node A ←——→ Node B   ✗   Node C
           网络中断，无法通信
```

这不是假设，而是现实：网络抖动、机房光缆断裂、云厂商的网络故障，都可能造成分区。

---

## 三个特性的精确含义

### Consistency（强一致性）

所有节点上的数据完全一致。任何读操作，**无论访问哪个节点**，都能读到最新写入的数据。

```
客户端写入 x=2 到 Node A
↓
Node A 同步到 Node B（成功才返回）
↓
客户端读 Node B，得到 x=2  ✓
```

注意：这里的 Consistency 是**强一致性**，不是数据库 ACID 里的 C（那个 C 是约束不被违反）。

### Availability（可用性）

每个请求都必须收到一个响应（成功或失败），不能无限等待或直接拒绝服务。

注意：可用性不要求返回的数据是最新的，只要求系统"回应"你。

### Partition Tolerance（分区容忍性）

当网络发生分区（部分节点间断连）时，系统仍然能够继续运行，不能直接崩溃。

---

## 为什么 P 必须保留

假设你放弃 P——也就是说，一旦出现网络分区，你的系统就停止工作。

在单机系统里这没问题，网络断了就断了。

但在分布式系统里，你有多台机器通过网络连接，网络分区**不是"如果"而是"何时"的问题**。如果你放弃 P，本质上你的系统在任何网络抖动时都会停服，这不可接受。

**结论：分布式系统必须容忍分区，P 不可放弃。真正的选择是 CP 还是 AP。**

---

## CP vs AP：当分区发生时，你选择哪个

### CP 系统：保一致性，牺牲可用性

当网络分区发生时，**拒绝服务**，直到分区恢复、数据同步完成。

```
Node A 和 Node B 分区了
客户端请求 Node B 读数据
Node B："我不确定 Node A 上有没有更新，我拒绝响应"
客户端收到错误
```

典型例子：
- **ZooKeeper**（分布式协调服务）
- **HBase**
- 银行转账系统（宁可暂时不可用，也不能出现数据不一致）

### AP 系统：保可用性，牺牲一致性

当网络分区发生时，**继续提供服务**，但不保证所有节点的数据完全一致。

```
Node A 和 Node B 分区了
客户端写入 x=2 到 Node A
网络断了，Node B 还是 x=1
另一个客户端读 Node B，得到 x=1（旧数据）
```

分区恢复后，系统会自动同步，最终数据会一致。这叫**最终一致性（Eventual Consistency）**。

典型例子：
- **Cassandra**（可配置）
- **DynamoDB**
- DNS 系统（更新全球 DNS 记录需要时间，不同地区暂时看到不同结果）
- 购物车系统（宁可暂时显示旧数据，也不能让用户无法使用）

## 一个具体的例子：购物网站

你在做一个电商网站，商品库存数量存在分布式数据库里，部署在上海和北京两个机房。

**网络分区发生了（上海机房和北京机房断连）。**

**选择 CP：**
- 所有库存相关操作报错："系统繁忙，请稍后"
- 用户无法下单
- 没有超卖风险
- 损失了这段时间的销售额

**选择 AP：**
- 两个机房独立工作，用户可以继续下单
- 上海用户和北京用户都能抢同一件商品
- 可能发生超卖（库存只剩 1 件，被卖出 2 件）
- 需要在业务层补偿（退款给其中一个用户）

没有绝对正确的选择，取决于**业务的容忍边界**：超卖+补偿 vs 短暂不可用，哪个代价更高？

## CAP 定理的局限性

CAP 定理是 2000 年提出的，它有一些局限性，实际工程中要注意：

### 1. 一致性和可用性不是非黑即白

CAP 把它们描述成二元选择，但实际上是一个**连续的谱**：

- 你可以选择"写入时同步 2 个节点中的 1 个就返回成功"（部分一致性）
- 也可以选择"写入时同步所有节点才返回成功"（强一致性）

不同的配置对应不同的 consistency level（一致性级别），后面在 `04_distributed/01_consistency_models.md` 会详细讲。

### 2. 分区不是常态

正常情况下网络是通的，CAP 的矛盾只在分区发生时才出现。平时 CP 系统的可用性其实和 AP 系统差不多。

### 3. PACELC 模型（扩展版）

PACELC 是对 CAP 的扩展：

```
如果 发生分区（P）：选择 可用性（A）或一致性（C）
否则（E）：在 延迟（L）和一致性（C）之间取舍
```

即使没有分区，你仍然要在延迟和一致性之间权衡：
- 写入时等所有副本确认 → 强一致性，但 latency 高
- 写入时只等一个节点确认 → 低 latency，但暂时不一致

---

## 常见数据库的 CAP 定位

| 数据库 | 类型 | 说明 |
|--------|------|------|
| MySQL（主从复制） | CP | 默认情况下牺牲可用性保一致性 |
| PostgreSQL | CP | 同上 |
| MongoDB | CP（可配置为 AP） | 默认强一致，可调 |
| Cassandra | AP | 高可用，最终一致性 |
| DynamoDB | AP（可配置） | 默认最终一致，可选强一致读 |
| ZooKeeper | CP | 严格一致性，用于分布式协调 |
| Redis Cluster | AP | 分区时可能丢数据 |

---

## 与 Node.js/TS 生态的类比

你可能用过 Redis 做缓存。单机 Redis 不存在 CAP 问题（单机就是一个节点）。

但如果你用 **Redis Cluster**（多节点分片），就要面对 CAP 选择了。Redis Cluster 选择的是 AP：

```typescript
// 正常情况
await redis.set('user:1:balance', 100);
const balance = await redis.get('user:1:balance'); // 100

// 网络分区时
await redis.set('user:1:balance', 90);  // 写入 Node A
// Node A 和 Node B 分区
const balance = await redis.get('user:1:balance'); // 可能读到 Node B，返回 100（旧值）
```

这就是为什么 Redis 不适合存储需要强一致的金融数据。

---

## 常见陷阱

1. **以为可以同时满足 CAP 三者**：不可能，定理已被数学证明
2. **认为 AP 就是"不一致"**：AP 是分区时暂时不一致，分区恢复后会最终一致
3. **选了 CP 就以为数据永远一致**：CP 只在单次操作的语义上保证，跨操作的一致性需要额外机制（事务）
4. **忽略分区恢复后的冲突处理**：AP 系统在分区恢复后，两个节点上的数据可能有冲突，需要设计冲突解决策略（Last-Write-Wins、向量时钟等）

## 面试常见问答

### 简单

**Q：什么是 CAP 定理？**

A：CAP 定理指出，一个分布式系统不可能同时满足：Consistency（强一致性，所有节点数据相同）、Availability（可用性，每个请求都有响应）、Partition Tolerance（分区容忍性，节点间断连时系统仍工作）这三个特性，最多只能同时满足其中两个。由于网络分区在真实分布式系统中不可避免，P 必须保留，所以实际选择是 CP 还是 AP。

---

**Q：请举一个 CP 系统和一个 AP 系统的例子，并解释为什么。**

A：CP 系统例子：ZooKeeper。用于分布式协调（选主、分布式锁），要求所有节点看到一致的状态，分区时宁可拒绝请求也不能返回脏数据。AP 系统例子：Cassandra。设计目标是高可用，分区时各节点继续独立服务，接受暂时的数据不一致，分区恢复后通过 gossip 协议同步。选择依据是业务容忍度：数据不一致的代价 vs 服务不可用的代价哪个更高。

---

**Q：为什么说分布式系统必须容忍分区，P 不可放弃？**

A：因为网络分区是分布式系统的物理现实，不是假设场景。机房光缆故障、网络抖动、云厂商故障都可能造成节点间断连。如果放弃 P，意味着一旦出现任何网络问题就整体停服，这比选择 CP 或 AP 更糟糕——CP 最多拒绝部分请求，AP 最多返回旧数据，而放弃 P 是完全不可用。

---

### 中等

**Q：CAP 定理中的 Consistency 和 ACID 中的 Consistency 有什么区别？**

A：两者完全不同，只是碰巧用了同一个词。CAP 的 C 是**分布式一致性**：在分布式系统中，所有节点在同一时刻看到相同的数据（类似于"同步"的概念）。ACID 的 C 是**数据完整性约束**：事务执行前后，数据库的约束规则（如外键、非负余额）不被违反，数据从一个合法状态变成另一个合法状态。前者是关于多节点数据同步，后者是关于单个数据库的业务规则守护。

---

**Q：一个电商系统在设计库存扣减功能时，应该选 CP 还是 AP？为什么？**

A：应该选 CP。库存扣减是强一致性场景，超卖会造成直接的商业损失（发货不出去、赔付、客诉）。宁可在网络分区时拒绝下单请求（用户看到"系统繁忙，请稍后"），也不能允许两个机房各自独立扣减导致库存超卖。而用户评论数、浏览记录这类功能可以选 AP，短暂的数据不一致完全可以接受。

---

**Q：AP 系统在分区恢复后，两个节点数据冲突了怎么处理？**

A：这是 AP 系统设计中最难的问题，常见策略有：
- **Last Write Wins（LWW）**：用时间戳决定，时间戳最新的值获胜。简单但有时钟偏差问题，可能丢数据
- **向量时钟（Vector Clock）**：记录每次写入的版本因果关系，检测真正的冲突，由应用层或用户决定如何合并
- **CRDT（Conflict-free Replicated Data Types）**：设计特殊数据结构，使任意顺序合并都能得到确定结果（如购物车用 set 而不是 list）
- **业务层补偿**：允许超卖，但事后退款或补货，把技术冲突转化为业务流程

---

### 难

**Q：CAP 定理已经被证明，但有人说它"过时了"或"不准确"，你怎么看？**

A：CAP 定理本身的数学证明是正确的，但它的表达过于简化，有几个局限性：
1. **一致性和可用性是连续谱，不是二元**：实际系统可以在强一致到最终一致之间选择任意点（Cassandra 的 quorum 配置就是例子），CAP 把它简化成了非此即彼
2. **分区是小概率事件**：CAP 只描述分区发生时的行为，忽略了正常状态下的 latency vs consistency 权衡，PACELC 模型补充了这一点
3. **可用性的定义很宽**：CAP 的 A 只要求"有响应"，但实际系统中响应超时、降级响应是否算"可用"，定义很模糊

所以 CAP 是一个有用的思维框架，帮助你理解权衡，但不能机械套用。实际选型要用更细粒度的工具，比如 PACELC、quorum 配置、一致性级别。

---

**Q：如果让你设计一个"在网络分区时既能保证可用性，又尽量减少数据不一致"的系统，你会怎么做？**

A：核心思路是**缩小不一致的范围和时间窗口**，而不是消除它：
1. **减少跨分区写入**：通过一致性哈希或地理分片，让用户的数据尽量只在一个分区内操作，减少跨分区冲突的概率
2. **使用 quorum 读写**：写入时要求 W 个节点确认，读取时读 R 个节点取最新值，通过调整 W + R > N 来控制一致性强度
3. **冲突可检测**：引入版本号或向量时钟，让系统能检测出哪些数据在分区期间被并发修改了
4. **业务操作幂等化**：分区恢复后重放操作时，幂等操作不会产生副作用（扣库存操作设计成"设置为某值"而不是"减去某值"）
5. **监控分区持续时间**：分区超过阈值时主动告警，人工介入决策，而不是让系统无限期地在不一致状态下运行
