# 网络基础：TCP / HTTP / DNS / CDN

## TL;DR

- **TCP**：可靠的字节流传输，有握手、有确认、有重传——代价是有 latency 开销
- **UDP**：不可靠的数据报传输，没有握手——代价是可能丢包，但 latency 低
- **HTTP/1.1 → HTTP/2 → HTTP/3**：每一代都在解决上一代的性能瓶颈
- **DNS**：把域名翻译成 IP 地址的分布式系统，本身就是最终一致性的实践
- **CDN**：把内容"搬"到离用户最近的地方，本质是用空间换时间

---

## TCP 和 UDP

### 为什么需要传输层协议

IP 层只管"把数据包送到目标 IP"，它不关心：
- 包有没有到达
- 包乱序了怎么办
- 两台机器同时发数据会不会混在一起

TCP 和 UDP 在 IP 层之上解决这些问题，但策略完全不同。

### TCP（Transmission Control Protocol）

TCP 提供**可靠的、有序的字节流**传输。

**三次握手（建立连接）**

```
客户端                          服务器
  |---SYN(seq=x)--------------->|   "我想连接你"
  |<--SYN-ACK(seq=y, ack=x+1)--|   "好的，我准备好了"
  |---ACK(ack=y+1)------------->|   "我知道了，开始传数据"

握手完成，可以传数据
```

为什么要三次？两次握手服务器无法确认客户端能收到自己的包，可能白占资源。

**代价**：每次建立新连接要额外花一个 RTT（Round Trip Time，往返时间）。RTT 是多少？同城约 1ms，跨大洲约 150ms。在弱网环境下，握手本身的代价就很显著。

**TCP 的可靠性机制：**
- **序列号**：每个字节都有编号，接收方重新排序
- **确认号（ACK）**：收到数据后回复确认
- **重传**：超时没收到 ACK，就重发
- **流量控制**：接收方告诉发送方"我能处理多快"，避免被淹没
- **拥塞控制**：检测网络拥堵，主动降速

**四次挥手（断开连接）**

```
客户端                          服务器
  |---FIN------------------->|   "我发完了"
  |<--ACK--------------------|   "知道了"
  |<--FIN--------------------|   "我也发完了"
  |---ACK------------------->|   "知道了，连接关闭"
```

四次的原因：关闭是半双工的，双方各自发送 FIN，各自确认。

### UDP（User Datagram Protocol）

UDP 是**无连接的、不可靠的**数据报传输。

发出去就发出去了，不管对方有没有收到，不重传，不保序。

```
客户端                          服务器
  |---数据包1---------------->|
  |---数据包2---------------->|
  |---数据包3---------------->|   （可能丢掉了）
  没有 ACK，没有重传
```

**UDP 的优势：**
- 没有握手，发就发了，latency 极低
- 没有头部开销，传输效率高
- 天然支持广播和组播

**UDP 适合什么：**
- **视频/音频流**：丢一帧没关系，卡顿比延迟更难受
- **DNS 查询**：一问一答，查询包很小，丢了重发一次即可
- **游戏**：位置同步，旧的位置数据过期就没价值了，不如发新的
- **HTTP/3**：基于 UDP 实现的 QUIC 协议（后面讲）

## HTTP 的演进

### HTTP/1.1

HTTP/1.1 是你最熟悉的版本，基于 TCP。

**核心问题：队头阻塞（Head-of-Line Blocking）**

HTTP/1.1 是串行的：一个连接里，上一个请求没有完成，下一个请求不能发送。

```
连接 1：[请求图片1——响应]  [请求图片2——响应]  [请求图片3——响应]
                                  ↑
               图片1 响应完才能发图片2 的请求
```

**解决方案（当时）**：浏览器对同一域名开 6 个并行 TCP 连接。但每个连接都要握手，开销大。

**Keep-Alive**：HTTP/1.1 引入了连接复用，一个 TCP 连接可以发多个 HTTP 请求，避免每次都握手。但还是串行的。

### HTTP/2

HTTP/2 的核心改进是**多路复用（Multiplexing）**。

```
一个 TCP 连接，同时传输多个请求/响应的帧（Frame）：

TCP 连接
  ├── 流1：[请求图片1的帧] ←→ [响应图片1的帧]
  ├── 流2：[请求图片2的帧] ←→ [响应图片2的帧]
  └── 流3：[请求图片3的帧] ←→ [响应图片3的帧]
                全部并行
```

**HTTP/2 的其他改进：**
- **头部压缩（HPACK）**：HTTP 头部很冗余，每次都要发 User-Agent、Cookie 等，HPACK 对头部做压缩
- **Server Push**：服务器可以主动推送资源（实际使用效果不好，后来大多废弃了）
- **二进制协议**：HTTP/1.1 是文本协议，HTTP/2 是二进制帧，解析更高效

**HTTP/2 残留的问题**：
虽然应用层多路复用了，但底层仍然是一个 TCP 连接。如果这个 TCP 连接发生**丢包**，TCP 的重传机制会让所有流都等待——TCP 层的队头阻塞。

### HTTP/3 / QUIC

HTTP/3 的根本改变是：**把 TCP 换成了 QUIC（Quick UDP Internet Connections）**。

QUIC 基于 UDP，但在应用层自己实现了可靠传输，并且：

**解决了 TCP 队头阻塞**：
```
QUIC 连接
  ├── 流1：有自己独立的可靠传输
  ├── 流2：有自己独立的可靠传输
  └── 流3：丢包了，只有流3等待重传，流1和流2继续
```

**0-RTT 连接建立**：
TCP + TLS 需要 2-3 次 RTT 才能开始传数据。QUIC 把握手和 TLS 合并，第一次连接 1 RTT，再次连接 0 RTT（复用会话密钥）。

```
HTTP/1.1 + TLS 1.2：TCP握手(1RTT) + TLS握手(2RTT) = 3 RTT 后传数据
HTTP/2  + TLS 1.3：TCP握手(1RTT) + TLS握手(1RTT) = 2 RTT 后传数据
HTTP/3 (QUIC)：   QUIC握手(1RTT) = 1 RTT 后传数据
                   复用时：0 RTT
```

**对移动网络友好**：
移动设备切换 WiFi 和 4G 时，TCP 连接会中断（因为 IP 变了）。QUIC 用 Connection ID 而不是 IP+端口标识连接，IP 变了连接不中断。

## DNS（Domain Name System）

### 是什么

DNS 是把人类可读的域名（`www.example.com`）翻译成机器可读的 IP 地址（`93.184.216.34`）的分布式系统。

### 完整的 DNS 解析流程

```
浏览器输入 www.example.com
  ↓
1. 检查浏览器 DNS 缓存 → 有？直接用
  ↓（没有）
2. 检查操作系统 DNS 缓存（/etc/hosts 等）→ 有？直接用
  ↓（没有）
3. 查询本地 DNS 解析器（通常是路由器或 ISP 提供的）→ 有缓存？直接用
  ↓（没有）
4. 本地解析器查询根域名服务器（Root DNS Server）
   "你知道 .com 域在哪吗？"
   → "不知道具体，但 .com 的 TLD 服务器地址是 X.X.X.X"
  ↓
5. 本地解析器查询 .com TLD（Top-Level Domain）服务器
   "你知道 example.com 的权威 DNS 在哪吗？"
   → "权威服务器地址是 Y.Y.Y.Y"
  ↓
6. 本地解析器查询 example.com 的权威 DNS 服务器
   "www.example.com 的 IP 是多少？"
   → "93.184.216.34"
  ↓
7. 本地解析器缓存结果，返回给浏览器
8. 浏览器连接 93.184.216.34
```

**这个过程通常需要几十到几百毫秒**（如果没有缓存）。所以每次 DNS 查询都有缓存。

### TTL（Time To Live）

每条 DNS 记录都有一个 TTL，单位是秒，表示这条记录可以被缓存多久。

```
example.com.  300  IN  A  93.184.216.34
              ↑
              TTL = 300 秒，5 分钟内可以用缓存
```

TTL 是 DNS 最终一致性的核心：你更新了 DNS 记录，全球用户需要等待缓存过期（TTL 到期）后才会看到新地址。

**实践建议**：
- 平时：设较长 TTL（3600 秒）减少 DNS 查询量
- 准备迁移时：提前几天把 TTL 降低到 300 秒，这样迁移时新地址能更快传播

### 常见 DNS 记录类型

| 类型 | 作用 | 例子 |
|------|------|------|
| A | 域名 → IPv4 地址 | `api.example.com → 1.2.3.4` |
| AAAA | 域名 → IPv6 地址 | `api.example.com → 2001:db8::1` |
| CNAME | 域名 → 另一个域名的别名 | `www.example.com → example.com` |
| MX | 邮件服务器 | `example.com → mail.example.com` |
| TXT | 任意文本，常用于验证 | SPF、DKIM 验证 |

### DNS 与负载均衡

DNS 可以做简单的负载均衡：

```
api.example.com → [1.2.3.4, 1.2.3.5, 1.2.3.6]
每次查询轮流返回其中一个（Round Robin DNS）
```

**DNS 负载均衡的缺点**：
- 客户端会缓存 IP，在 TTL 内不会换 IP，所以实际分配不均
- 如果某个 IP 挂了，客户端不知道，还会继续尝试连接

所以 DNS 只适合粗粒度的流量分配，精细的负载均衡需要专门的负载均衡器。

## CDN（Content Delivery Network）

### 是什么

CDN 是一个遍布全球的服务器网络，把内容缓存在离用户最近的节点（称为 **PoP，Point of Presence** 或 **Edge Server**）上。

```
没有 CDN：
  上海用户 → 美国源服务器（150ms RTT）

有 CDN：
  上海用户 → 上海 CDN 节点（5ms RTT）→ （缓存命中，直接返回）
                                      → （未命中，去美国源服务器取，缓存后返回）
```

### CDN 的工作原理

**1. 用户请求资源（如图片）**

```
浏览器请求 https://cdn.example.com/image.jpg
  ↓
DNS 解析 cdn.example.com → CDN 厂商的智能 DNS 返回离用户最近的 CDN 节点 IP
  ↓
浏览器连接到上海 CDN 节点
```

CDN 的关键在于 DNS 这一步：CDN 厂商的 DNS 服务器知道用户的位置（通过请求来源 IP），返回离用户最近的节点 IP。

**2. CDN 节点处理请求**

```
CDN 节点收到请求
  ├── 缓存命中 → 直接返回（低 latency，源服务器无压力）
  └── 缓存未命中 → 回源（从源服务器取内容，缓存到本地，再返回给用户）
```

### CDN 适合缓存什么

**适合：**
- 静态资源：图片、CSS、JS、字体文件
- 视频流：分片的视频文件
- 大文件下载
- 可以被公开缓存的 API 响应

**不适合：**
- 用户私有数据（不同用户看到不同内容）
- 实时数据（价格、库存）
- 需要鉴权的内容（需要额外配置）

### CDN 的缓存失效

CDN 节点的缓存如何更新？

**方法1：TTL 过期**
设置 Cache-Control 头，告诉 CDN 缓存多久。

```
HTTP 响应头：
Cache-Control: max-age=86400   # 缓存 24 小时
```

**方法2：主动 Purge**
通过 CDN 厂商的 API 主动清除特定 URL 的缓存。发布新版本 JS 文件后，可以立即 purge。

**方法3：文件名带版本号**
```
旧版本：/static/app-v1.0.js
新版本：/static/app-v1.1.js
```
新文件名，CDN 没有缓存，自然回源取最新内容。这是最常见的前端实践（Webpack 的 contenthash 做的就是这件事）。

### CDN 的其他功能

现代 CDN 不只是静态文件缓存，还提供：

- **DDoS 防护**：大量恶意流量打到 CDN，源服务器不受影响
- **WAF（Web Application Firewall）**：在 CDN 层过滤恶意请求
- **SSL 终止**：SSL/TLS 握手在 CDN 节点完成，源服务器收到的是 HTTP
- **边缘计算（Edge Computing）**：在 CDN 节点运行代码（Cloudflare Workers、Lambda@Edge），不用回源

## 常见陷阱

1. **HTTP/2 多路复用不等于没有队头阻塞**：应用层解决了，TCP 层还有，HTTP/3 才真正解决
2. **DNS 更新不是立即生效的**：TTL 没过期之前，旧 IP 还在被使用；紧急迁移前要提前降 TTL
3. **CDN 缓存了动态内容**：忘记设置正确的 Cache-Control，导致不同用户看到同一份缓存的个性化内容
4. **以为 HTTPS 慢**：TLS 1.3 已经很快了，加密开销几乎可以忽略；HTTPS 的"慢"主要来自握手 RTT，HTTP/2 和 HTTP/3 都已经优化了
5. **把 CDN 当成唯一的性能解决方案**：CDN 只能解决静态内容的 latency，动态内容还是要优化数据库和应用层

## 负载均衡深度

### L4 vs L7 负载均衡

负载均衡器按工作的网络层分两类，选错会在面试中被追问。

**L4 负载均衡（传输层，Transport Layer）**

```
工作在 TCP/UDP 层，只看 IP 地址 + 端口，不解析 HTTP 内容

客户端 → L4 LB（只看 IP:Port）→ 后端服务器

特点：
  - 速度极快：不解析 payload，内核态转发，可达百万 QPS
  - 对任意协议透明：TCP、UDP、WebSocket、gRPC 都能转发
  - 无法做内容路由：不能按 URL 路径、HTTP Header 分流
  - 连接保持：TCP 连接建立后，这条连接内的所有包都路由到同一台后端
             （做不到请求级别的负载均衡）

适用：
  - 纯性能要求（游戏服务器、DNS）
  - 非 HTTP 协议
  - 作为 L7 LB 的前置（接受公网 TCP，再转 L7）

代表产品：AWS NLB、LVS、HAProxy（L4 模式）
```

**L7 负载均衡（应用层，Application Layer）**

```
工作在 HTTP/HTTPS 层，能解析请求内容

客户端 → L7 LB（解析 HTTP Header、URL）→ 后端服务器

特点：
  - 内容路由：
      /api/*  → API 服务集群
      /static/* → 静态资源服务器
      Host: admin.example.com → 管理后台
  - SSL 终止：L7 LB 解密 HTTPS，后端走 HTTP（减少后端 CPU 开销）
  - Header 操作：添加/删除/修改 HTTP Header（如添加 X-Real-IP）
  - 健康检查：能发 HTTP 请求检查后端，比 L4 的 TCP ping 更准确
  - Sticky Session：基于 Cookie 把同一用户路由到同一后端
  - 流量分割：按百分比分流（金丝雀发布）
  - 代价：性能不如 L4（需要解析 HTTP，用户态处理）

适用：
  - 绝大多数 Web 应用
  - 需要内容路由的微服务网关

代表产品：nginx、AWS ALB、Envoy、Traefik
```

**实际架构：L4 + L7 组合**

```
互联网
  ↓
[L4 NLB] ← 处理 TCP 连接，性能极高，DDoS 防护
  ↓
[L7 ALB/nginx] ← 处理 HTTP 路由、SSL 终止、限流
  ↓
[后端服务集群]
```

### 负载均衡算法

| 算法 | 原理 | 适用场景 | 问题 |
|------|------|---------|------|
| **轮询（Round Robin）** | 依次分配给每台服务器 | 请求处理时间均匀 | 忽略服务器性能差异 |
| **加权轮询（Weighted RR）** | 按权重分配（高性能机器多分） | 服务器配置不同 | 权重需手动维护 |
| **最少连接（Least Connections）** | 分配给当前连接数最少的服务器 | 长连接（WebSocket、数据库连接） | 新服务器会被瞬间打满 |
| **IP Hash** | 按客户端 IP 的 Hash 固定路由 | 需要 Sticky Session 但无 Cookie | NAT 后所有用户打同一台 |
| **随机（Random）** | 随机选择 | 简单场景，节点同质 | 可能不均匀 |

**实际推荐：**
```
无状态服务（API 服务）→ 轮询 or 最少连接
有状态服务（WebSocket 聊天）→ IP Hash or Cookie-based Sticky
性能差异大 → 加权轮询
```

### Sticky Session（会话粘性）

```
问题：某些服务在服务器本地存了状态（如上传进度、WebSocket 连接），
      如果下一个请求路由到另一台服务器，状态丢失。

解决方案一：Cookie-based Sticky（L7 LB）
  LB 给用户设置一个 Cookie（如 SERVERID=server-3）
  后续请求带这个 Cookie → LB 路由到 server-3
  
  问题：server-3 挂了，这些用户的会话失效
  
解决方案二：集中式状态存储（推荐）
  服务器本身无状态，状态存到 Redis 或数据库
  任何服务器都能处理任何请求
  这是最佳实践：水平扩展无障碍，服务器挂了无影响
  
  结论：设计时应尽量把服务做成无状态（Stateless），避免依赖 Sticky Session
```

### 健康检查与连接排除

**健康检查**

```
LB 定期检查后端实例是否健康：

L4 健康检查（TCP 探测）：
  尝试建立 TCP 连接，连接成功 = 健康
  快，但粗糙——进程还在但逻辑已崩溃时无法发现

L7 健康检查（HTTP 探测）：
  GET /health → 期望返回 200 OK
  后端代码在 /health 里检查数据库连接、内存等
  更准确，推荐做法
  
  实现示例：
    GET /health
    返回：{ "status": "ok", "db": "connected", "latency_ms": 2 }
    或：503 Service Unavailable（主动告知不健康）
```

**连接排除（Connection Draining）**

```
问题：服务器下线时，正在处理中的请求不能直接中断

解决：
  1. LB 停止把新请求路由到该实例
  2. 等待该实例处理完已有请求（有超时上限，如 30 秒）
  3. 超时后强制关闭

K8s 中：
  Pod 收到 SIGTERM → 不再接受新请求 → 处理完在途请求 → 退出
  preStop hook 可以在 SIGTERM 前做一些清理
```

### BGP Anycast（全球流量调度）

```
场景：全球用户都访问同一个 IP（如 1.1.1.1），
      如何让上海用户打到上海节点，纽约用户打到纽约节点？

BGP Anycast：
  多个地理位置不同的服务器宣告同一个 IP 地址
  BGP 路由协议把用户的请求自动路由到"网络拓扑上最近"的节点

  上海用户 → BGP 路由 → 上海节点（1.1.1.1）
  纽约用户 → BGP 路由 → 纽约节点（同一个 1.1.1.1）

用途：
  - DNS 服务器（Cloudflare 1.1.1.1 就是 Anycast）
  - DDoS 防护（攻击流量被分散到多个节点）
  - 全球 CDN 边缘节点路由

与 DNS 负载均衡的区别：
  DNS LB：返回不同的 IP（用户解析到不同 IP）
  Anycast：同一个 IP，由网络层路由到不同节点（对用户透明）
```

### 面试常见问答（负载均衡）

**Q：你的聊天系统里有 WebSocket 连接，加了负载均衡后怎么处理？**

A：WebSocket 是长连接，连接建立后需要保持到同一台 Chat Server。在 L7 LB 层配置基于 Cookie 或 Connection ID 的 Sticky Session，确保同一个 WebSocket 连接的所有数据包到同一台服务器。更好的做法是让 Chat Server 无状态——WebSocket 连接状态存入 Redis，这样任何 Chat Server 实例都能处理同一用户的消息，LB 可以自由路由，不需要 Sticky。

**Q：L4 和 L7 负载均衡如何选？**

A：取决于需求：如果只需要 TCP 转发、追求极高性能（百万 QPS），用 L4；如果需要基于 URL 的内容路由、SSL 终止、HTTP Header 操作、更准确的健康检查，用 L7。生产中两者常组合使用：公网入口用 L4 NLB 处理 TCP 和 DDoS，内部再用 L7 nginx/ALB 做 HTTP 路由和 SSL 终止。

## 面试常见问答

### 简单

**Q：TCP 和 UDP 的核心区别是什么？各自适用什么场景？**

A：TCP 是面向连接的、可靠的传输协议，通过握手建立连接、ACK 确认、超时重传保证数据完整有序到达，代价是有延迟开销。UDP 是无连接的、不可靠的协议，直接发包，没有握手和确认，延迟低但可能丢包乱序。适用场景：TCP 用于需要可靠传输的场景（HTTP、数据库连接、文件传输）；UDP 用于延迟敏感且能容忍少量丢包的场景（视频通话、在线游戏、DNS 查询）。

---

**Q：HTTP/1.1 的队头阻塞（Head-of-Line Blocking）是什么？HTTP/2 怎么解决的？**

A：HTTP/1.1 在一个 TCP 连接上请求是串行的，前一个请求的响应没回来，后一个请求不能发送，导致后面的请求"排队等头部"。HTTP/2 引入了多路复用（Multiplexing）：把一个 TCP 连接切分成多个逻辑流（Stream），多个请求/响应的数据帧并行传输，互不阻塞。

---

**Q：DNS 的 TTL 是什么？修改 DNS 记录后为什么不立刻生效？**

A：TTL（Time To Live）是 DNS 记录的缓存时间（单位秒），告诉解析器可以缓存这条记录多久。修改 DNS 记录后不立刻生效，是因为全球各地的 DNS 解析器都缓存了旧记录，必须等它们各自的 TTL 到期才会重新查询获取新值。TTL 设为 300 秒，最长需要 5 分钟传播；设为 86400 秒（1天），可能要等 1 天才能全球生效。

---

### 中等

**Q：HTTP/2 已经解决了应用层队头阻塞，为什么还需要 HTTP/3？**

A：HTTP/2 的多路复用在应用层解决了队头阻塞，但底层仍然是一个 TCP 连接。TCP 保证有序传输，一旦某个数据包丢失，TCP 必须等待重传，这期间整个连接的所有流都会被阻塞——这是 TCP 层的队头阻塞，HTTP/2 无法解决。HTTP/3 把底层协议换成了基于 UDP 的 QUIC，QUIC 在应用层自己实现可靠传输，每个流独立管理丢包重传，一个流丢包不影响其他流。此外 QUIC 还支持 0-RTT 连接建立和连接迁移（IP 变化不断连），对移动端和弱网更友好。

---

**Q：CDN 是如何做到让用户访问"最近"节点的？**

A：核心是 DNS 路由。CDN 厂商控制自己的权威 DNS 服务器，当用户查询 CDN 域名时，DNS 服务器根据用户的来源 IP 判断其地理位置，返回距离最近（或网络质量最好）的 CDN 节点 IP。这个过程对用户完全透明，用户只知道域名，看不到背后的节点选择逻辑。更精细的 CDN 还会用 anycast 路由：同一个 IP 地址部署在多个节点，网络层自动把请求路由到最近的节点。

---

**Q：什么时候应该把 DNS TTL 设低？什么时候设高？有什么代价？**

A：设低 TTL（60-300 秒）：需要快速切换流量时，比如蓝绿部署、灾难切换、IP 变更。代价是 DNS 查询量增大，每个用户都要频繁重新查询，对 DNS 服务器有压力，也增加了解析延迟（TTL 内走缓存是 0ms，每次查询要几十到几百 ms）。设高 TTL（3600-86400 秒）：内容稳定不变时，减少 DNS 查询，用户访问更快，DNS 服务器压力小。代价是变更生效慢。最佳实践：平时用高 TTL，在计划变更前 24-48 小时提前降低 TTL，变更完成稳定后再升回去。

---

### 难

**Q：TCP 三次握手为什么是三次，两次为什么不够？四次可以吗？**

A：三次握手的目的是让双方都确认"对方能发，我也能收；我能发，对方也能收"。
- 第一次（客户端→服务器 SYN）：服务器知道客户端能发
- 第二次（服务器→客户端 SYN-ACK）：客户端知道服务器能发且能收（ACK 证明服务器收到了第一次），也让服务器知道客户端能收
- 第三次（客户端→服务器 ACK）：服务器知道客户端能收（ACK 证明客户端收到了第二次）

两次握手不够：服务器发出 SYN-ACK 后，无法确认客户端是否收到，如果丢失，服务器会以为连接建立成功并分配资源，造成资源浪费。更严重的是，历史上的旧 SYN 包（网络中滞留的）可能导致服务器建立无效连接。

四次可以但没必要，三次已经是最小满足条件的次数。

**Q：设计一个全球部署的服务，用户在上海、纽约、伦敦，如何减少这些用户的访问延迟？**

A：分层优化：

1. **静态内容**：部署 CDN，全球边缘节点缓存静态资源，用户就近访问。图片、JS、CSS 延迟可以从 150ms 降到 5ms
2. **动态内容（API）**：在三个地区各部署一套应用服务器（多地域部署），DNS 智能解析把用户路由到最近的区域。这样上海用户打上海的 API，不用跑到美国
3. **数据库**：这是最难的部分。只读请求可以用读副本（各地区一个 replica）；写请求通常只有一个主节点，远程写入延迟不可避免。方案选项：
   - 主写节点选在用户最密集的地区，其他地区接受写延迟
   - 用 Global Database（如 Aurora Global、CockroachDB）支持多地域写入，但有一致性限制
   - 数据按地区分片（上海用户数据在上海 DB），各地区写本地，牺牲跨地区数据查询能力
4. **协议优化**：用 HTTP/2 或 HTTP/3，减少握手 RTT；API Gateway 和应用服务器之间用 gRPC 长连接，复用连接减少握手开销
5. **连接预热**：用户打开 App 时就预先建立到最近服务器的连接（Connection Pool 预热），用户真正操作时不需要等待握手
