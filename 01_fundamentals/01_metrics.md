# 可靠性指标：Latency / Throughput / Availability

## TL;DR

- **Latency（延迟）**：一个请求从发出到收到响应花了多长时间
- **Throughput（吞吐量）**：系统单位时间内能处理多少请求
- **Availability（可用性）**：系统在一段时间内"正常工作"的比例

这三个指标是系统设计中最基础的度量标准。每次做设计决策时，都要问：这个决策如何影响这三个数字？

---

## Latency（延迟）

### 是什么

Latency 是时间的度量。从客户端发出请求，到客户端收到完整响应，这段时间就是 latency。

```
客户端         服务器
   |--请求-------->|
   |               | 处理中
   |<--响应--------|
   |←————————————→|
         latency
```

### 为什么不能只看平均值

假设你有 100 个请求，99 个耗时 10ms，1 个耗时 10000ms。

- **平均值**：(99×10 + 10000) / 100 ≈ 109ms
- **P99**：10000ms

平均值是 109ms，看起来还好。但实际上有 1% 的用户在等 10 秒。这就是为什么工程师不看平均值，而是看**百分位数（percentile）**。

### 百分位数（Percentile）

| 指标 | 含义 |
|------|------|
| P50（中位数） | 50% 的请求在这个时间内完成 |
| P95 | 95% 的请求在这个时间内完成，最慢的 5% 超过这个值 |
| P99 | 99% 的请求在这个时间内完成，最慢的 1% 超过这个值 |
| P999 | 99.9% 的请求在这个时间内完成 |

**实际工作中通常关注 P99**。P99 代表"最慢的那批用户"的体验，如果 P99 很差，说明有相当数量的用户在忍受糟糕的体验。

### Latency 的组成

一个请求的 latency 由多个部分叠加而成：

```
total latency = 网络传输时间 + 排队时间 + 处理时间 + 数据库查询时间 + ...
```

- **网络传输时间**：受物理距离限制，光速约 200,000 km/s，上海到纽约单程约 75ms
- **排队时间**：服务器繁忙时请求在队列里等待
- **处理时间**：CPU 计算时间
- **I/O 时间**：磁盘读写、数据库查询

### 关键数字（要记住）

这些数字是做容量估算时的基础直觉：

| 操作 | 延迟数量级 |
|------|-----------|
| L1 cache 访问 | ~0.5 ns |
| 内存访问 | ~100 ns |
| SSD 随机读 | ~100 μs |
| HDD 随机读 | ~10 ms |
| 同城网络往返 | ~0.5 ms |
| 跨大洲网络往返 | ~150 ms |

> **记忆技巧**：内存比 L1 cache 慢 200 倍，SSD 比内存慢 1000 倍，HDD 比 SSD 慢 100 倍，网络比内存慢 5000 倍。

## Throughput（吞吐量）

### 是什么

Throughput 是速率的度量。系统在单位时间内能处理多少工作量。

对于 Web 服务，通常用 **QPS（Queries Per Second，每秒请求数）** 或 **RPS（Requests Per Second）** 表示。

对于数据管道，通常用 **每秒处理多少 MB/GB 数据** 表示。

### Latency 与 Throughput 的关系

它们不是独立的，有时候是矛盾的：

**场景 1：低并发**
- 10 个用户同时请求，每个请求处理 10ms
- Latency: 10ms，Throughput: 1000 QPS（理想情况）

**场景 2：高并发**
- 10000 个用户同时请求，服务器 CPU 打满
- 每个请求处理时间变成 100ms（排队等 CPU）
- Latency 上升了，Throughput 达到了瓶颈

这就是为什么**提升 Throughput 经常会牺牲 Latency**，两者需要平衡。

### 吞吐量的瓶颈在哪里

系统的吞吐量由**最慢的那个环节**决定，这叫**木桶效应**：

```
[客户端] → [负载均衡] → [应用服务器] → [数据库]
              10万QPS      5000QPS       1000QPS
                                           ↑
                                        瓶颈在这
```

即使应用服务器能处理 5000 QPS，数据库只能处理 1000 QPS，整个系统的吞吐量上限就是 1000 QPS。

## Availability（可用性）

### 是什么

Availability（可用性）是系统"正常工作时间"占总时间的比例。

```
Availability = 正常工作时间 / (正常工作时间 + 宕机时间)
```

通常用百分比表示，也叫**几个九**：

| 可用性 | 年宕机时间 | 月宕机时间 |
|--------|-----------|-----------|
| 99%（两个九） | 87.6 小时 | 7.2 小时 |
| 99.9%（三个九） | 8.76 小时 | 43.8 分钟 |
| 99.99%（四个九） | 52.6 分钟 | 4.4 分钟 |
| 99.999%（五个九） | 5.26 分钟 | 26.3 秒 |

**大多数商业系统要求三个九到四个九**。五个九非常难，意味着全年宕机不超过 5 分钟，包括计划内维护。

### 为什么可用性难以提升

每增加一个"九"，工程难度指数级上升：

- **两到三个九**：避免单点故障，做主从备份即可
- **三到四个九**：需要多地域部署、自动故障转移、灰度发布
- **四到五个九**：需要多活架构、混沌工程、秒级故障自愈

### 串联系统的可用性

如果系统由多个组件串联（A 调用 B，B 调用 C），整体可用性是各组件可用性的**乘积**：

```
可用性 = A × B × C
       = 99.9% × 99.9% × 99.9%
       = 99.7%
```

这就是为什么微服务架构中，调用链不能太长——每多一个依赖，可用性就乘以一个小于 1 的数。

### 并联系统的可用性

如果系统有冗余（两台服务器任意一台正常就能提供服务）：

```
可用性 = 1 - (1 - A) × (1 - B)
       = 1 - (1 - 99%) × (1 - 99%)
       = 1 - 0.01 × 0.01
       = 99.99%
```

两个 99% 的节点并联，可以达到 99.99%。**冗余是提升可用性的最直接手段。**

## SLA / SLO / SLI

这三个词经常混用，但含义不同：

| 缩写 | 全称 | 含义 | 例子 |
|------|------|------|------|
| **SLI** | Service Level Indicator（服务等级指标） | 实际测量到的指标 | "过去 1 小时 P99 latency 是 120ms" |
| **SLO** | Service Level Objective（服务等级目标） | 内部定的目标 | "P99 latency 应低于 200ms" |
| **SLA** | Service Level Agreement（服务等级协议） | 对外签的合同 | "保证 99.9% 可用性，否则退款" |

**关系**：SLI 是实测值，SLO 是内部目标，SLA 是对外承诺。

通常 SLA < SLO，因为内部目标要比对外承诺更严格，留有缓冲。

例如：内部 SLO 是 99.95% 可用性，对外 SLA 承诺 99.9%，这样即使稍微没达到 SLO，也不会违反 SLA。

## 与 Node.js/TS 生态的类比

你写 Express 服务时可能遇到过：

```typescript
// 这段代码的 latency 是多少？
app.get('/user/:id', async (req, res) => {
  const user = await db.query('SELECT * FROM users WHERE id = ?', [req.params.id]);
  res.json(user);
});
```

- **Latency**：从请求进入到 `res.json()` 执行完毕的时间，主要由 `db.query()` 决定
- **Throughput**：Node.js 单线程事件循环，I/O 密集型可以处理很高的并发；但如果 `db.query()` 慢，所有请求都会排队
- **Availability**：如果这台服务器挂掉，整个服务就挂了——这就是为什么需要多实例部署

---

## 常见陷阱

1. **只看平均 latency**：P99 才是真正反映用户体验的指标
2. **认为 latency 和 throughput 是独立的**：提升 throughput 通常会让高百分位的 latency 上升
3. **忽略串联组件的可用性乘法**：微服务调用链每多一跳，可用性就下降一点
4. **把 SLA 和 SLO 混用**：SLA 是合同，违反有法律/商业代价；SLO 是内部目标，用来驱动工程改进

## 面试常见问答

### 简单

**Q：什么是 P99 latency？为什么不用平均值？**

A：P99 latency 是指 99% 的请求都在这个时间内完成，只有最慢的 1% 超过这个值。不用平均值是因为平均值会被少量极端慢的请求"稀释"——99 个 10ms 加 1 个 10000ms，平均才 109ms，但有 1% 的用户在等 10 秒，平均值掩盖了真实的用户体验问题。

---

**Q：什么是 SLA？和 SLO 有什么区别？**

A：SLA（Service Level Agreement）是对外签署的服务协议，规定了可用性或性能的承诺，违反会有商业或法律代价。SLO（Service Level Objective）是内部制定的目标，通常比 SLA 更严格，给 SLA 留缓冲。SLI（Service Level Indicator）是实际测量到的指标值。三者关系：SLI 是实测，SLO 是内部目标，SLA 是对外承诺，严格程度 SLO > SLA。

---

**Q：99.9% 可用性意味着一年允许多少宕机时间？**

A：约 8.76 小时（365 × 24 × 0.001 ≈ 8.76）。99.99% 是约 52 分钟，99.999% 是约 5 分钟。

---

### 中等

**Q：如果你的系统有 3 个微服务串联调用，每个服务可用性是 99.9%，整体可用性是多少？**

A：串联系统可用性是各组件乘积：99.9% × 99.9% × 99.9% ≈ 99.7%。这就是微服务拆分的隐性代价——调用链越长，可用性越低。应对方式包括：引入熔断器（Circuit Breaker）快速失败、设计降级策略让部分服务不可用时整体仍可用、减少不必要的同步调用链。

---

**Q：latency 和 throughput 之间有什么关系？能同时优化两者吗？**

A：两者经常存在矛盾。提高 throughput 通常需要批量处理或提高并发，这会让请求在队列中等待更长时间，导致高百分位 latency 上升。反过来，为了降低 latency 而减少批量处理，throughput 会下降。能同时优化的情况是：当前瓶颈是低效的代码或不合理的串行 I/O，通过异步化、连接池等方式可以同时提升两者。设计时需要明确业务优先级：延迟敏感型（在线交易）还是吞吐优先型（日志处理）。

---

**Q：如何度量一个分布式系统的可用性？"正常工作"如何定义？**

A：可用性 = 成功请求数 / 总请求数，或者 = 正常服务时间 / 总时间。"正常工作"需要在 SLO 中明确定义，比如"HTTP 状态码为 2xx 且 latency < 500ms 的请求比例"。不同团队定义不同，有些用错误率（Error Rate < 0.1%），有些用延迟（P99 < 200ms），关键是提前和业务对齐定义。

---

### 难

**Q：你负责的服务 P99 latency 突然从 50ms 飙升到 2000ms，你怎么排查？**

A：按层次逐步缩小范围：
1. **确认影响范围**：是所有接口还是特定接口？是所有用户还是特定地区？
2. **看系统资源**：CPU、内存、网络 I/O 是否打满？Node.js 的 Event Loop lag 是否异常？
3. **看依赖调用**：数据库查询时间、Redis 响应时间、第三方 API 是否变慢？用 APM（如 Datadog、Jaeger）追踪每段耗时
4. **看时间相关性**：飙升时间点是否有部署、配置变更、流量突增？
5. **看错误日志**：是否有超时、连接池耗尽、GC 停顿（Java/Go）？
6. **假设最常见原因**：数据库慢查询（缺索引、数据量增大）、连接池不足、外部依赖超时未设置、内存泄漏导致 GC 频繁。

---

**Q：设计一个 SLO 监控系统，要求能实时检测 SLO 违反并告警。你会怎么设计？**

A：核心是"错误预算（Error Budget）"的实时消耗追踪。
- **数据采集**：在服务层采集每个请求的 latency 和状态码，写入时序数据库（Prometheus/InfluxDB）
- **SLI 计算**：滑动窗口（如过去 1 小时）内计算成功率和 P99 latency
- **错误预算**：例如 SLO 是 99.9%，一个月错误预算 = 0.1% × 30天 = 43.8 分钟。实时追踪预算消耗速率
- **告警策略**：不能简单阈值告警（会产生大量噪音），要用"预算消耗速率"：如果当前速率下，预算会在 6 小时内耗尽，立即告警；预算消耗超过 50%，发预警
- **可视化**：Grafana 大盘展示 SLI 趋势、错误预算剩余量、近 24 小时违规事件
- **实现参考**：Google SRE 书中的 Error Budget 概念，Alertmanager 的 for 条件用于避免瞬间抖动触发告警
