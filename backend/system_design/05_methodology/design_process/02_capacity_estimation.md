# 容量估算方法论

## TL;DR

容量估算不是精确计算，是建立**数量级感知**：差 10 倍是大问题，差 2 倍无关紧要。

核心公式：
- **QPS** = 日活 × 每人操作次数 / 86400
- **存储** = 每条数据大小 × 每天新增量 × 保存时间
- **带宽** = 峰值 QPS × 单次请求数据量

---

## 为什么要估算

容量估算让你在设计时知道：

- 读 QPS 是 100 还是 100 万？前者不需要缓存，后者必须有
- 存储是 10GB 还是 10PB？前者单机搞定，后者要分布式存储
- 写 QPS 是 10 还是 10 万？前者单库，后者要分片或 NoSQL

错了一个数量级，整个架构的选型就错了。

## 基础数字（背下来）

### 时间换算

```
1 分钟 = 60 秒
1 小时 = 3600 秒
1 天   = 86400 秒 ≈ 10 万秒（估算时用 10^5）
1 年   = 3150 万秒 ≈ 3 × 10^7 秒
```

### 数据单位

```
1 KB = 10^3 字节
1 MB = 10^6 字节
1 GB = 10^9 字节
1 TB = 10^12 字节
1 PB = 10^15 字节
```

### 常见数据大小

| 内容 | 大小 |
|------|------|
| ASCII 字符 | 1 字节 |
| UTF-8 中文字符 | 3 字节 |
| 一条短文本（推文，280字）| ~500 字节 |
| 一条数据库行（元数据）| ~100-500 字节 |
| 一张缩略图 | ~10-50 KB |
| 一张高清图片 | ~1-5 MB |
| 一分钟 720p 视频 | ~60-100 MB |
| 一封邮件（含附件平均）| ~100 KB |
| 一页 PDF | ~100 KB |

### 延迟参考

| 操作 | 延迟 |
|------|------|
| L1 缓存读 | 0.5 ns |
| 内存读 | 100 ns |
| SSD 随机读 | 100 μs |
| 机械硬盘随机读 | 10 ms |
| Redis 操作（本地） | 0.1 ms |
| 数据库查询（带索引） | 1-10 ms |
| 同城网络往返 | 0.5 ms |
| 跨大洲网络往返 | 150 ms |

## QPS 估算方法

### 基本公式

```
平均 QPS = 日活用户(DAU) × 每人每天平均操作次数 / 86400
峰值 QPS = 平均 QPS × 峰值系数
```

**峰值系数经验值：**
- 普通 B2C 产品：2-5 倍（早晚高峰）
- 电商大促（双十一）：10-20 倍
- 偶发热点（重大新闻）：50-100 倍

### 分离读写 QPS

大多数系统读写比例悬殊，要分开估算：

```
社交产品：读写比约 100:1（看帖子的人 >> 发帖子的人）
搜索：纯读，写是索引更新（异步）
消息系统：写 ≈ 读（每条消息被读一次）
日志系统：写 >> 读（日志写入多，查询少）
```

### 示例：设计 Instagram

```
假设：
  DAU = 5 亿
  每人每天看 20 张图片（读）
  每人每天发 0.01 张图片（写，100人里1人发）

读 QPS：5亿 × 20 / 86400 ≈ 116,000 QPS
写 QPS：5亿 × 0.01 / 86400 ≈ 58 QPS

峰值读 QPS ≈ 580,000 QPS → 必须有多层缓存
峰值写 QPS ≈ 290 QPS → 单机 MySQL 轻松处理
```

## 存储估算方法

### 基本公式

```
每日新增存储 = 每日新增条目数 × 每条大小
总存储 = 每日新增 × 保存天数
```

**常用保存期限：**
- 社交内容：永久（或 5-10 年）
- 日志：30-90 天
- 缓存：按 TTL，不计入总存储
- 冷数据可以归档到便宜存储（磁带、冷 S3）

### 示例：Twitter 推文存储

```
每天新增推文：
  日活 1 亿 × 发推率 0.1 = 1000 万条/天

每条推文大小：
  文本（280字 UTF-8）：280 × 2字节 ≈ 600 字节
  元数据（用户ID 8字节 + 时间戳 8字节 + 其他 50字节）：66 字节
  合计约 700 字节 ≈ 1 KB

每日存储：
  1000万 × 1KB = 10 GB/天

5年总存储：
  10 GB × 365 × 5 ≈ 18 TB → 分布式存储，单机不够
  
媒体文件（图片/视频）另算：
  假设 10% 的推文带图片，图片平均 2 MB
  100万张 × 2MB = 2 TB/天 → 需要对象存储（S3）
```

## 带宽估算

```
峰值带宽（下行）= 峰值读 QPS × 每次响应大小
峰值带宽（上行）= 峰值写 QPS × 每次请求大小
```

### 示例

```
Instagram 图片浏览：
  峰值读 QPS = 58 万
  每张图片缩略图 = 50 KB
  下行带宽 = 58万 × 50KB = 29 GB/s = 232 Gbps

  → 这就是为什么 Instagram 需要 CDN，
    单个数据中心根本没这个带宽
```

## 服务器数量估算

```
单台应用服务器：
  CPU 密集型：~1000 QPS
  I/O 密集型（Node.js）：~10,000-50,000 QPS
  （视业务逻辑复杂度而定）

单台 MySQL：
  读：~5000-20000 QPS（有索引）
  写：~3000-10000 QPS

单台 Redis：
  ~100,000 QPS（单线程，CPU 密集操作会降低）

单台 Kafka Broker：
  ~100 MB/s 写入 ≈ 1,000,000 条/秒（每条 100 字节）
```

## 估算的心态

**准确到数量级就够了：**

```
精确计算：
  5亿 × 20 / 86400 = 115,740.7 QPS
  
数量级估算：
  5亿 × 20 / 10万 ≈ 10万 QPS → "十万 QPS 量级"
```

面试中用后者。精确计算浪费时间，且会给人"抓细节、缺全局观"的印象。

**用 10 的幂次：**
```
1 亿 = 10^8
10 万 = 10^5
100 万 = 10^6
```

乘除法直接用指数加减，快速估算：
```
10^8 × 10^1 / 10^5 = 10^4 = 1 万 QPS
```

## 估算在设计中的应用

估算完成后，立刻得出关键结论：

| 指标 | 结论 |
|------|------|
| 读 QPS > 1 万 | 需要缓存层（Redis） |
| 读 QPS > 10 万 | 需要多级缓存或 CDN |
| 写 QPS > 1 万 | 考虑数据库分片或 NoSQL |
| 每天存储 > 1 TB | 需要分布式存储 |
| 总存储 > 10 TB | 考虑对象存储（S3） |
| 带宽 > 10 Gbps | 需要 CDN |

## 面试常见问答

### 简单

**Q：如何估算一个系统的 QPS？**

A：基本公式：QPS = DAU（日活用户）× 每人每天平均操作次数 / 86400（一天的秒数）。峰值 QPS 通常是平均的 2-5 倍。面试时重点要拆分读 QPS 和写 QPS——大多数系统读远多于写，读 QPS 决定缓存策略，写 QPS 决定数据库选型。

---

### 中等

**Q：面试官给你一个没有任何数字的题目（设计 YouTube），你如何建立估算基础？**

A：先自己提出合理假设，大声说出来让面试官确认或纠正：
"我先做几个假设：DAU 10 亿；每人每天看 5 个视频；每人每天上传 0.01 个视频（100 人里 1 人上传）；每个视频平均 10 分钟，720p 压缩后约 600 MB。"
然后基于这些假设估算：读 QPS ≈ 58000，写 QPS ≈ 116，每天新增视频存储 ≈ 116 × 600MB ≈ 70 TB。
关键不在于数字是否精确，而是展示你知道什么数字重要，以及估算思路是否清晰。
