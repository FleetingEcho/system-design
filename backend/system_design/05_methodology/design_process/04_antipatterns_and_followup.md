# 反模式识别 + 被追问应对

## TL;DR

面试扣分不只来自"说错"，更多来自"踩了常见陷阱"或"被追问时答不下去"。这篇文档覆盖两件事：
1. **7 个高频反模式**：面试官听到就会往下追问甚至扣分的设计
2. **被追问框架**：面试官追问时的标准应对节奏

---

## 七个高频反模式

### 反模式 1：过早分片（Premature Sharding）

**症状**：系统刚上线，预估 QPS 才 1000，就设计了 16 个分片。

**为什么是问题：**
```
分片一旦确定，改起来代价极高：
  - 跨分片事务（Saga/2PC）复杂性
  - 跨分片查询需要 scatter-gather，延迟高
  - 重新分片（re-shard）需要数据迁移，风险大

单台 MySQL 能抗 5000~1 万 QPS（读写混合）
单台 PostgreSQL 更高

正确顺序：
  1. 先单库，建好索引，读写分离
  2. 加缓存（Redis Cache-Aside），读压力降 80%+
  3. 读写分离从库扩展（1主3从）
  4. 到了真正瓶颈再分片，且要先测量再决策
```

**面试中如何表达：**
> "当前规模用单库加缓存可以应对，我先设计这个路径；如果增长到 X QPS，会考虑按 [分片键] 水平分片，分片键选择的依据是..."

---

### 反模式 2：同步调用链过长

**症状**：
```
用户下单 → 同步调用库存服务 → 同步调用支付服务 → 同步调用通知服务 → 返回
```

**为什么是问题：**
```
链中任一服务慢/超时 → 整个链超时
链中任一服务挂了 → 订单失败

延迟叠加：
  每个服务 50ms → 4个串行 = 200ms（最好情况）
  任一服务 P99 = 500ms → 用户感知 500ms+

实际问题：你的 P99 latency = max(所有服务的 P99)
  4个服务 P99 各 100ms → 组合 P99 ≈ 340ms（1-(0.99)^4）
```

**正确做法：**
```
下单核心路径只做必须同步的事：
  同步：扣库存（必须立即确认）+ 创建订单记录
  异步：发通知、更新统计、触发推荐系统更新

发消息到 Kafka，各下游服务异步消费
用户立即拿到订单号，后续通知异步送达
```

### 反模式 3：缓存当主存储

**症状**：把重要数据只存 Redis，不落地数据库，或把 Redis 当数据库主存。

**为什么是问题：**
```
Redis 默认的持久化模式（RDB）：
  每 N 秒做一次快照，宕机可能丢 N 秒内的数据

Redis AOF 模式：
  每次写入都记日志，持久性更好，但重启后 replay 很慢

Redis Cluster 脑裂：
  主节点宕机期间，新主可能不包含最新数据

结论：Redis 是缓存，不是数据库
  - 主数据 → 关系型数据库 or NoSQL（带副本、持久化保证）
  - Redis → 加速读取、临时状态、计数器
```

**面试中如何表达：**
> "这部分数据是 Cache-Aside 模式：写入时先写数据库再淘汰缓存，读取时优先读 Redis，Redis miss 时回源数据库。Redis 只做加速，不是 Source of Truth。"

### 反模式 4：全局分布式锁滥用

**症状**：任何需要"互斥"的地方都用 Redis 分布式锁（SETNX）。

**为什么是问题：**
```
分布式锁的代价：
  - 每次加锁/解锁 = 一次 Redis 网络往返（1~5ms）
  - Redis 故障时，锁服务不可用 → 整个功能不可用
  - 锁超时设置难：太短会误释放，太长会阻塞

锁可以避免的情况：
  1. 数据库乐观锁（version 字段 + CAS UPDATE）
     适合：低冲突率的更新（库存扣减、余额变更）
     
  2. 数据库行锁（SELECT FOR UPDATE）
     适合：同一 DB 内的互斥，不需要跨服务

  3. 原子操作（Redis INCR/DECR、Lua 脚本）
     适合：计数器、简单扣减，比分布式锁快

  分布式锁适合：
     跨服务的互斥（A 服务和 B 服务不能同时执行同一任务）
     定时任务防重复执行
```

### 反模式 5：忽略幂等性

**症状**：设计 API 时没有考虑"如果同一请求发来两次怎么办"。

**为什么是问题：**
```
重试是网络的基本行为：
  - 超时重试（客户端等了 3 秒没回应，再发一次）
  - 消息队列 at-least-once（消息可能被消费两次）
  - 网关重试（nginx upstream 超时自动重试）

不幂等的后果：
  - 重复扣款（用户被扣两次钱）
  - 重复发货（订单被创建两次）
  - 重复发通知（用户收到两条相同推送）
```

**正确做法：**
```
客户端生成 idempotency_key（UUID），随请求发送
服务端：
  1. 检查 Redis 是否有这个 key（已处理过）
  2. 没有：执行业务逻辑，把结果存入 Redis（TTL = 24h）
  3. 有：直接返回存储的结果

数据库层：对 idempotency_key 字段建 UNIQUE 索引
  INSERT INTO orders (idempotency_key, ...) 
  ON CONFLICT (idempotency_key) DO NOTHING
```

### 反模式 6：单点故障（Single Point of Failure）

**症状**：架构图里某个组件只有一个实例，没有备份。

**常见 SPOF：**
```
- 单台数据库（主库宕机，整个系统写不了）
- 单台消息队列（Kafka 只有 1 个 broker）
- 单台 API Gateway
- 单个机房（整个数据中心断电）
```

**面试中被追问时的标准回答框架：**
```
对每个关键组件，问自己：
  "如果这个组件挂了，系统会怎样？"
  
  数据库主库挂了 → 从库自动提升（需要秒级 failover，如 MHA/Orchestrator）
  缓存 Redis 挂了 → 降级到直接查 DB（性能差但不崩溃）
  消息队列挂了 → 同步处理降级（限流保护）
  
原则：
  有状态组件 → 主从复制 + 自动故障转移
  无状态组件 → 多实例 + 负载均衡
  外部依赖 → 熔断器 + 降级逻辑
```

### 反模式 7：强一致用在不需要的地方

**症状**：用户名、头像、点赞数这类数据也要求强一致，导致每次写入都需要多副本同步确认。

**为什么是问题：**
```
强一致的代价：
  - Quorum 写（W+R > N）：延迟高
  - 2PC：性能差，单点问题
  - 分区时拒绝写入（CP 系统）

不是所有数据都需要强一致：
  强一致（必须）：
    - 金融账户余额、库存计数（不能出错）
    - 分布式锁、Leader 选举
    - 唯一性约束（用户名不能重复）

  最终一致（可以接受）：
    - 用户头像、个人简介（改了几秒后全球同步）
    - 点赞数、播放量（±1% 误差可接受）
    - 搜索索引（新内容 1 分钟后可被搜到）
    - 朋友圈 Feed（发帖后粉丝有几秒延迟）
```

**面试中如何表达：**
> "这个数据是用户个人资料，修改后有几秒的传播延迟用户能接受，所以用最终一致——主库写入后异步同步到从库和缓存，用户最多看到几秒前的版本。"

## 被追问应对框架

面试官的追问通常属于以下四类，每类有标准应对节奏。

### 追问类型 1："这个组件挂了怎么办？"

**面试官意图**：验证你考虑了容错，不是纸上谈兵。

**应对框架（30 秒内说完）：**

```
1. 说影响范围："如果 [组件] 挂了，受影响的是 [什么功能]"
2. 说检测："通过 [健康检查/心跳] 在 [多久] 内发现故障"
3. 说恢复："触发 [自动 failover/降级/报警]"
4. 说代价："在 [X 秒内] 期间，[什么体验降级]，但 [核心数据不丢失/服务不崩溃]"

例子：
"如果 Redis 缓存挂了，读请求会落到数据库，
 延迟从 1ms 升到 10ms，QPS 能力从 10 万降到 1 万。
 我们会在监控里看到 Redis 健康检查失败，自动触发告警。
 降级期间数据库会承压，需要限流保护（比如只接受 80% 的请求）。
 Redis 恢复后缓存自动预热，影响消除。"
```

---

### 追问类型 2："为什么用 X 而不用 Y？"

**面试官意图**：验证你的选型有依据，不是随便说的。

**应对框架：**

```
1. 确认你理解 Y 是什么（"Y 是..."）
2. 说 X 和 Y 的关键差异（1-2 个维度）
3. 说你的场景的决定性因素

模板："Y 在 [场景] 下很好用，但我们的场景是 [特点]，所以 X 更合适，
      因为 X 在 [决定性维度] 上 [比较优势]，代价是 [X 的缺点]，
      我们接受这个代价因为 [业务原因]。"

例子（为什么用 Kafka 不用 RabbitMQ）：
"RabbitMQ 更适合传统消息队列场景，支持复杂路由、TTL、死信队列，
 但我们的场景是广告点击日志，写入量极高（100 万/秒），
 且需要消费历史数据做重放和审计，Kafka 的 append-only log + partition
 在高吞吐和数据回放上更有优势，代价是不支持复杂路由逻辑，
 但我们的消费模型简单，不需要这个能力。"
```

---

### 追问类型 3："如何 Scale 这个组件？"

**面试官意图**：验证你知道当前设计的极限在哪里，以及如何突破。

**应对框架：**

```
1. 说出当前设计的瓶颈点
2. 水平扩展方案
3. 下一个瓶颈是什么（说明你想到了更深的层次）

例子（Scale 数据库写入）：
"当前单主库，写入瓶颈大约在 5000 QPS。
 第一步：Kafka 缓冲写入，批量写数据库，可以把实时 QPS 降到 500。
 第二步：如果 Kafka 也满足不了，按用户 ID 分片，每个分片独立主库，
          16 分片理论上支持 8 万 QPS。
 第三步：再往上就需要考虑列式存储（ClickHouse）
          或者时序数据库，取决于查询模式。"
```

---

### 追问类型 4："并发 / 竞态条件怎么处理？"

**面试官意图**：验证你不只是画了一个架构图，还考虑了多实例同时运行时的正确性。

**应对框架：**

```
先分析是否真的存在竞态：
  两个操作 A 和 B，是否可能同时执行且互相影响？
  
  如果是：
    同一数据库内 → 数据库事务 + 行锁（FOR UPDATE）或乐观锁（version）
    跨服务 → 分布式锁 or Saga 补偿
    幂等操作 → 直接幂等化（天然不怕并发，因为结果一样）
    
  如果不是（操作作用于不同数据）→ 不需要锁

例子（用户同时购买最后一件库存）：
"两个用户同时看到库存为 1，然后都点了购买。
 解决方案：数据库原子更新 + 检查影响行数：
   UPDATE inventory SET stock = stock - 1 
   WHERE product_id = ? AND stock >= 1
   
 如果 affectedRows = 1，购买成功；
 如果 affectedRows = 0，说明被别人抢先了，返回'库存不足'。
 这是乐观锁的一种形式，不需要显式锁，高并发下性能更好。"
```

## 快速诊断清单

面试结束前 2 分钟，快速扫一遍你的设计：

```
□ 有没有单点故障？（每个组件都有备份或降级方案）
□ 有没有长同步调用链？（非关键路径是否异步化）
□ 核心数据是否只存了缓存？（Redis 里的重要数据有没有落库）
□ 幂等性有没有考虑？（接口是否能安全重试）
□ 有没有滥用锁？（是否有更轻量的替代方案）
□ 强一致的代价是否合理？（用弱一致是否已足够）
□ 选型有没有说出"为什么"？（而不只是说"我用 Kafka"）
```
